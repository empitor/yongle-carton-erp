# 升级前只读核对

这一版带业务库升级步骤时，发布前（第 2 步）在服务器上做。全部只读：在正式库或补丁前的完整备份上跑，**先问用户**；只读打开库（`sqlite3 -readonly <库文件>`，或 Node 的 `new DatabaseSync(库文件, { readOnly: true })`），不在正式库上写任何东西。每一节只管写明的那几步，这几步上了服务器就整节删掉。

## 服务器上点名跑升级测试（第 24、25 步）

第 24 步用到 `json_patch`、`json_group_array`，第 25 步用到 `UPDATE … FROM`、窗口函数、递归 CTE、`json_set`，只在开发机的 Node（SQLite 3.51）上跑过。在服务器上取这一版的源码（取法同第 5 步），点名跑 `tests/core/upgrade-step-samples.test.ts`、`tests/core/schema-upgrade.test.ts`，不过就停。

## 从 0.9.5 升上来之前查的数（第 23 到 25 步）

在 0.9.5 的业务库上（还没升级）跑，结果报给用户，好先打招呼或先处理。

**1. 收货信息超长的老待送货单。** 第 25 步不给它们挂厂区，升级后再保存会换成所选或默认厂区的收货信息，手填的没了（`docs/计划/已知问题.md`）。列出来的能出库的先出库，剩下的记下单号，升级后到客户档案补厂区再在单上选。

```sql
-- 只读：升级前的库里，第 25 步会因收货信息超长而不挂厂区的待送货单（这些单升级后再保存，仍按所选或默认厂区重取收货信息）。
-- 口径和第 25 步一样：没挂厂区的待送货单（归档的也算）、客户还在、三项去首尾空白（空白同 JS 的 trim）后不全空；
-- 按 JS 字符串长度（四字节的字算 2）比厂区录入的上限：联系人 60、联系方式 50、地址 300；带 NUL 的算超长（字数写 -1）。
-- 字数只数到第 300 个字，超过 300 的照“至少这么多”显示。
WITH RECURSIVE upto(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM upto WHERE i<300),
drafts AS (
  SELECT d.id, d.number, c.name AS customer,
    trim(coalesce(json_extract(d.document,'$.address'),''),char(9,10,11,12,13,32,160,5760,8192,8193,8194,8195,8196,8197,8198,8199,8200,8201,8202,8232,8233,8239,8287,12288,65279)) AS address,
    trim(coalesce(json_extract(d.document,'$.contact'),''),char(9,10,11,12,13,32,160,5760,8192,8193,8194,8195,8196,8197,8198,8199,8200,8201,8202,8232,8233,8239,8287,12288,65279)) AS contact,
    trim(coalesce(json_extract(d.document,'$.phone'),''),char(9,10,11,12,13,32,160,5760,8192,8193,8194,8195,8196,8197,8198,8199,8200,8201,8202,8232,8233,8239,8287,12288,65279)) AS phone
  FROM flow_documents d JOIN customers c ON c.id=json_extract(d.document,'$.customerId')
  WHERE d.kind='delivery' AND d.status='draft' AND json_extract(d.document,'$.siteId') IS NULL
),
measured AS (
  SELECT id, number, customer,
    CASE WHEN instr(contact,char(0))>0 THEN -1 ELSE length(contact)+(SELECT count(*) FROM upto WHERE i<=length(contact) AND unicode(substr(contact,i,1))>65535) END AS contact_len,
    CASE WHEN instr(phone,char(0))>0 THEN -1 ELSE length(phone)+(SELECT count(*) FROM upto WHERE i<=length(phone) AND unicode(substr(phone,i,1))>65535) END AS phone_len,
    CASE WHEN instr(address,char(0))>0 THEN -1 ELSE length(address)+(SELECT count(*) FROM upto WHERE i<=length(address) AND unicode(substr(address,i,1))>65535) END AS address_len
  FROM drafts WHERE address||contact||phone<>''
)
SELECT number AS 单号, customer AS 客户, contact_len AS 联系人字数, phone_len AS 联系方式字数, address_len AS 地址字数
FROM measured
WHERE contact_len<0 OR phone_len<0 OR address_len<0 OR contact_len>60 OR phone_len>50 OR address_len>300
ORDER BY id;
```

**2. 订单里没带 % 的小数税率和三位小数。** 0.9.5 照 0.13%、13.125% 直接算钱；升级后认不出（`0.13` 可能是 13%，不猜），这些订单新开的送货单进“资料待补”，要人补税率。下面是粗查，按写法列条数：

```sql
SELECT tax_rate AS 写法, count(*) AS 条数
FROM (SELECT tax_rate FROM orders UNION ALL SELECT tax_rate FROM order_lines)
WHERE tax_rate IS NOT NULL AND instr(tax_rate,'%')=0 AND instr(tax_rate,'％')=0
  AND (trim(tax_rate) GLOB '*.[0-9][0-9][0-9]*'
    OR (CAST(trim(tax_rate) AS REAL)>0 AND CAST(trim(tax_rate) AS REAL)<1))
GROUP BY tax_rate ORDER BY 条数 DESC;
```

**3. 三项以外的含税口径。** 列出来的里，首尾带空白的“含税”“未税”“未明确”和“不含税”升级时认得出；别的写法照抄成“口径：…”留在原话里，这些订单新开的送货单记资料待补。`quote` 让首尾空白看得见：

```sql
SELECT '订单' AS 表, quote(tax_mode) AS 写法, count(*) AS 条数 FROM orders
WHERE tax_mode IS NOT NULL AND tax_mode<>'' AND tax_mode NOT IN ('含税','未税','未明确') GROUP BY tax_mode
UNION ALL
SELECT '明细', quote(tax_mode), count(*) FROM order_lines
WHERE tax_mode IS NOT NULL AND tax_mode<>'' AND tax_mode NOT IN ('含税','未税','未明确') GROUP BY tax_mode;
```

**4. 往来单位默认税率的小数写法。** 往来条款的税率格单位是 %，填 0.13 就按 0.13% 补扫算钱；列出来看有没有其实想写 13% 的：

```sql
SELECT tax_rate AS 写法, count(*) AS 条数 FROM fin_party_terms
WHERE tax_rate IS NOT NULL AND instr(tax_rate,'%')=0
  AND (tax_rate GLOB '*.[0-9][0-9][0-9]*' OR (CAST(tax_rate AS REAL)>0 AND CAST(tax_rate AS REAL)<1))
GROUP BY tax_rate ORDER BY 条数 DESC;
```
