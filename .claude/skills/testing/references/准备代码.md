# 测试的准备代码

搭环境只用共用的准备代码（`tests/support/*-fixture.ts`，各家族专用的放在自己的目录里，如财务的在 `tests/finance/`），不在测试文件里再抄一份：

| 要什么 | 用哪个 |
|---|---|
| 起真实服务 | `http-fixture.ts`：`startHttp`（登录好，`h.enterSuperMode()` 进超级管理员模式），`startProxied` 模拟从域名经代理访问，`listen` 不要登录 |
| 借一个账号 | `actor-fixture.ts`：`pageActor`、`actor`、`superActor`；换权限写 `{ ...actor, permissions: grant(...) }`（`grant` 只收权限名单里的名字） |
| 从结果取数 | `read-result.ts`：`readAs` 按结构取、`must` 一定有 |
| 建档和预览再核对 | 只用 `business-base-fixture.ts` 的 `businessBase`（常用的一套 `standardRecords`）；别的准备代码都在它上面搭，交出来叫 `base`（测试里写 `f.base`） |
| 一套虚构业务数据 | `stack-fixture.ts`（`stackFixture`）、`flow-fixture.ts`（`flowFixture`、`businessFixture`、`workbenchFixture`） |
| 各模块自己的 | 财务 `finance-fixture.ts`，单据导出 `document-fixture.ts`，助手 `assistant-fixture.ts`（自动确认 `autoConfirmAssistant`），模型替身 `fake-deepseek.ts`，能卡住的密码哈希 `hash-gate.ts` 等 |

几条常用的写法：

- 常用的准备代码（`flowFixture`、`businessFixture`、`workbenchFixture`、`maintenance-fixture`、`admin-edit-fixture`、`delete-fixture` 的 `setup`、`completionFixture`、`deliveryCorrectionSetup`）都交出 `base`：补建档写 `f.base.customer(...)`，核对单据写 `f.base.check(单据, 别的字段, 谁)`；没有准备代码的写 `businessBase(谁, store)`。只有测预览本身、过期、重发的才自己写 `flow.preview` 加 `flow.confirm`。生产任务直接保存（`task()`），不交给 `confirm`。
- 要按页面保存客户、产品、订单并触发审计或快照，用 `tests/support/business-base-fixture.ts` 的 `manualWrite`。
- 建助手用 `tests/support/assistant-fixture.ts` 的 `assistantDeps`（或 `assistantFixture`），只测业务工具用 `toolsOf`、`ctxOf`，只测业务流程用 `autoConfirmAssistant`；建识别导入管理器用 `tests/support/order-import-fixture.ts` 的 `testImports`。
- 要完整视图（已安排、可用、到货记录、单号）用 `FlowService` 的 `views`，改已有采购单、库存品和手工出入库用 `flow.stock.*`。
- 财务测试要“假装业务变了”（直接造已确认的单据、改单据内容、撤销、删除、删流水、挪流水日期、改库存品）只用 `tests/support/business-changes-fixture.ts` 的 `businessChanges(store)`，不在测试里直接写业务表的 SQL；测“库里内容坏了、读不出来”用它的 `tamper(...)`（模拟直接改库，版本号不动）。
- 直接调财务服务的测试不会自动补扫（只有路由和助手入口会）。财务看来源撤没撤销、删没删只走 `server/finance/events/source-scan.ts` 的 `sourceIs`，所以测“撤销后”的写入拦截不用先补扫；成本计算里“已撤销”只认窗口的 `stock.reversedArrivals`。
