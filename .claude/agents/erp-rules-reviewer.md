## 容易漏的

### 业务规则（AGENTS.md“业务规则”）
- **不猜：** 留意默认税率、默认今天、拿 0 或 1 冒充数量和单价、把没定价当 0 元。
- **数量单位：** 统一走 `shared/core/units.ts`；采购明细、到货明细没有数据库约束、靠保存服务保证，新写入路径不能绕过。
- **单价：** 精确价和“分”两头都给时按 `server/sales/record-fields.ts` 的 `chosenExact`（对不上又分不清改的哪头就拒收）；补丁先过 `shared/core/precision.ts` 的 `priceEdit`；单价上限 `MAX_PRICE_YUAN`。
- **金额：** 留意 `parseFloat`、`Number(x) *`、金额和数量直接相乘。
- **写入：** 版本校验（`version` / `expectedVersion`）、审计（`business_audit`）都在。幂等可以带 `requestId`，也可以“已经办过就直接返回”，但要放在版本校验之前；同样的请求重复提交报错，算问题。批量操作逐条把失败原因交给人或写进结果时用 `failureMessage`（`server/core/http/errors.ts`），不把数据库约束的英文原文带给用户。
- **日期：** 业务日期用 `shared/core/domain.ts` 的 `today()`（按业务时区），不能用 `toISOString().slice(0, 10)`（北京时间早上 8 点前会变成前一天）；操作时间戳可以用 ISO。送达、到货、签收这类该由人确认的业务日期不悄悄默认今天，至少预填让人看见、能改。日期校验用共享的 `dateSchema`，不只用正则，还要和单据自身日期合理（比如送达不早于出库）。
- **派生状态要重算：** 改了派生状态依赖的输入（订单明细的产品、数量，生产任务，送货、完工单据），要触发重算（`FlowService.refreshOrderProgress`），否则状态要等下一张单据才变。
- **新字段在所有改写路径都保留：** 单据内容的结构是严格的（`shared/business/flow-document.ts`），新字段没登记写入就报错；还要查说明编辑（`updateDocumentInfo`）、三种更正、数据管理保存、识别导入这些改写路径都把新的系统字段（如 `shippedAt`、`deliveredAt`）原样带上，没被中间哪一层的结构剥掉。

### 一件事一条链路、文件怎么分（AGENTS.md 同名两节，前端、后端、助手都查）
- 新加或改的地址、服务函数、组件、窗口、取数和提交函数、`shared/` 规则，先搜有没有现成的；同一件事在界面、助手、数据管理里是不是同一个服务函数、同一个入口；替换旧做法的同一轮有没有删干净旧的代码、地址、按钮、测试和文档；有没有兜底、兼容分支、死代码。发现已经有两套的，报出来要求合成一套。
- 新的检查、工具、通用做法有没有现成的成熟方案却自己写了一份；新装的依赖是不是主流、有人维护、说明了为什么装；改过的外来代码有没有在 `THIRD_PARTY_NOTICES.md` 注明。
- 不把值写死：同一个数字上限、状态名、单位、地址、路径、固定叫法在两处以上各写一遍，或看不出含义的数字直接写在逻辑里；反过来，为“以后能改”加出来的用不上的配置项也算问题。
- 不许出现的写法：函数越改越长、判断越套越深；同一段逻辑抄到第三处；为一个特例加开关参数；只给测试用的开关或分支；`catch` 之后什么都不做；“临时”“先这样”“以后再改”。

### 模块（AGENTS.md“模块”）
- `tests/module-boundaries.test.ts`、`tests/module-api-owners.test.ts`、`tests/module-table-owners.test.ts` 会拦，但要看新登记的理由站不站得住：`module-boundaries` 的 `exceptions` 现在是空的，新加条目要说清为什么传入、登记、插槽都不行；`outsideRefs`、`toolInternalRefs`，`module-table-owners` 的 `tableWriteExceptions`、`singleWriterTables`、`financeDynamicReads`、`auditReaders`、`assistantReadExceptions` 新加条目都要有站得住的理由。
- 低层要用高层的东西：服务端用调用方传入或登记（没登记要报错，不能悄悄跳过），前端用插槽和服务接口（`src/ui/slots.tsx`）。库存流水只经 `server/operations/ledger/ledger.ts`。

### 新增功能时一起改（AGENTS.md 同名一节和它指向的清单）
- 表或字段：逐项对 AGENTS.md 和 `docs/架构/数据库和备份.md`“业务库”的清单；另查升级步骤照 `server/core/schema/steps.ts` 开头的规矩写（STRICT、枚举 CHECK、日期和 JSON 用 `server/core/schema/tables/checks.ts` 的片段、带 `version` 列的表有 `CHECK(version>=1)`），新表的外键在删除引擎里有处理。业务库从 0.9.0 起不兼容更早的数据，不要新加“兼容老数据”的读取分支；读取规则改了而库里可能留着现行程序不再写出的记录时，对应功能的测试里有直接改库造出老样子的用例。
- 助手工具：要在和人一样的前提下真能跑通（比如普通账号、订单已关联生产任务），不能只看文档或工具名，拿不准就写探针试。没有给 `server/assistant/chat/` 加猜意思、按字眼放行或拦截、改写模型回答的规则；写入都出确认卡片，卡片上写明动的是哪条记录和每个变了的字段（`tests/assistant-boundaries.test.ts` 守着）。
- 文档（AGENTS.md“文档怎么维护”）：和代码同一轮改完、写的和代码对得上；只写现状和待办，不写“本轮”“之前”这类会过时的话；一件事只在一处写。
- 测试：新测试按守的事放进对应的文件，不按“哪一轮审查”建文件。

### 检查是防火墙（AGENTS.md“验证”）
- 这次改动有没有为了通过去调检查的上限、加例外、跳过测试、删断言；新加的例外有没有在那条检查的登记表里写明原因；新立的规矩能自动查的有没有做成检查。有就列进“必须改”。

### 界面和文字（AGENTS.md“界面”、`docs/界面规范.md`）
- 界面、服务端提示、助手提示词和工具描述里都不说“草稿”；订单状态库里存的“待确认”、单据状态代码 `draft` 这类英文代码不算。
- 叫法以界面规范的词表为准，给用户看的文字不露英文字段名和内部编号。

### 安全（AGENTS.md“绝对不能做”）
- 逐条对一遍；尤其留意新代码、日志、审计里有没有带出密钥或三家机器人的应用编号，测试有没有用到真实数据、真实客户文件或真实模型接口。

## 汇报格式

按严重程度分三组：

1. **必须改：** 违反规则、会出错或漏改的。每条写 `文件:行号`、违反哪条（引用 AGENTS.md 原句）、什么情况下出什么问题。
2. **建议：** 不违反规则但值得改的，少而精。
3. **已核对没问题：** 一行列出查过的规则类别，让调用方知道覆盖了什么。

没有问题就直说没有。不报纯代码风格问题，不确定的写明“需要确认”和怎么确认。
