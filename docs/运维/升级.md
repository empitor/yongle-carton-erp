# 升级

什么时候读：升级服务器或本机（打补丁、换整包、回滚、退回旧版本、碰到 0.9.0 以前的旧数据）。

维护命令怎么运行，备份、恢复、换回配置库的命令，相关的见 `docs/运维/部署.md`、`docs/运维/备份恢复.md`。

## 补丁（小版本）

小版本只传变化的程序文件；大版本（如 0.9.0）和依赖有变化时用整包。**服务器上跑的必须是 GitHub 上某个已发布版本**：本机、GitHub、服务器三方除数据、配置、密钥和 `node_modules` 外程序文件逐字节相同。所以先发布（提交、打 `v版本号` 标签、推送、建 GitHub 发布，步骤在 Claude Code 的 `/release` 技能里，发布说明就是 `docs/CHANGELOG.md` 那一节），再在维护电脑的项目目录打补丁（`--host` 是 SSH 配置里的主机名，默认 `yongle-erp`）：

```sh
npm run patch-server -- --dry-run
npm run patch-server
npm run patch-server -- --check
```

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只列差异。正式打之前检查本机没有未提交的改动、当前提交打了 `v版本号` 标签、GitHub 同名标签指向同一提交，不满足就拒绝 |
| `--check` | 列出三方版本和提交、逐个比对文件；一致退出码 0，不一致列原因、退出码 1 |
| `--hotfix "原因"` | 只用于服务器紧急故障：跳过发布检查直接打，服务器记“临时修复，未发布”，事后必须补发正式版 |
| `--base 旧版安装目录 --out 输出目录` | 只生成发布补丁、不上传：输出补丁文件和三个执行脚本 `apply-patch.mjs`、`patch-logic.mjs`、`patch-rollback.mjs`（各带 `.sha256`，清单是 `scripts/patch-server.mjs` 的 `applyScripts`），三个脚本放同一目录运行 |

出问题回滚：检出上一个版本标签再打一次，或用服务器上的回滚副本。

**补丁做了什么：**

- 只取 git 跟踪的程序文件（清单 `scripts/release-files.mjs`，和整包共用）；有没纳入 git 的、被忽略的、符号链接、通不过发布扫描的（数据库、密钥、证书）就拒绝；`package-lock.json` 变了也拒绝（补丁不能重装原生依赖）；`erp.env` 的 `ERP_CONFIG_DIR` 不是绝对路径直接拒绝（程序这时也起不来，先改 `erp.env`）。
- 本机类型检查、把页面构建到临时目录；和服务器逐个比 sha256（Windows 换行转 LF，`.cmd` 保持 CRLF）；上传变化的文件和 `scripts/linux/` 下的三个执行脚本。
- 服务器上先记下补丁开始时间和业务库结构版本、做完整备份、存回滚副本，再停服务、换文件、启动、查健康和版本；读不出版本或备份失败就什么都不改。只改 `/opt/yongle-carton-erp`，不碰配置。
- 同一时间只跑一个（锁 `/run/yongle-carton-erp-patch.lock`）；不怕 SSH 断开，全程记在 `/var/backups/yongle-carton-erp-patches/补丁编号/apply.log`，回滚副本 `rollback.json`（含补丁开始时间）也在那里。每次补丁记在程序目录的 `.release-package`（`commit` 当前提交、`released` 是否正式发布、`patches` 历次补丁）。

断线后查结果：

```sh
ssh yongle-erp sudo tail -n 40 /var/backups/yongle-carton-erp-patches/补丁编号/apply.log
npm run patch-server -- --check
```

日志最后是“补丁已应用”就成了；写着“回滚”或“补丁未应用”就是没打上，照日志处理。

**自动回滚：** 启动失败或 90 秒内健康检查不过，就停服务、换回旧文件，**先换回配置库，再看业务库**。

1. **配置库**（新程序启动时可能已升级了账号、提示词、AI 设置等，各库相关的见 `docs/生成/表结构.md`，旧程序会因“比程序新”起不来）：
   - 换回来的 `erp.sh` 有 `revert-config-upgrades` 动作：以服务账号运行它，把补丁开始以后升级过的配置库换回升级前备份；它报失败（见 `docs/运维/备份恢复.md`“换回配置库”）就转人工。
   - 没有这个动作（0.9.0 的程序）：在数据目录、配置目录各自的 `snapshots/` 里找补丁开始以后的配置库升级前备份（每个库最新一份），只读看库现在的版本，等于备份写的“到第几版”才算升级过。一个都没有就往下走；有、或读不出某个库的版本，转人工（提示列出是哪几个库和备份）。
   - **转人工：** 服务保持停止，照打印的步骤逐个换：把现在的库连同 `-wal`、`-shm`、`-journal` 改名留在 `snapshots/` 下（`<库文件名>-before-revert-manual-时间`，不要删），再把升级前备份复制回去。命令跑过但失败的，步骤只列还没换回的；之后又读不出版本时，列出补丁开始以后全部的配置库升级前备份，逐个确认库的版本等于备份写的“到第几版”才换。步骤里写明业务库变没变：没变换完直接启动，变了或判断不了接着用补丁前备份恢复。
   - 换回后，新程序运行期间改的配置（新账号、长期记忆、提示词、AI 设置、机器人设置）在换下来的 `-before-revert-` 文件里，要时人工补录；账号库换回后没有会话，**所有人要重新登录**。
2. **业务库：** 结构版本没变 → 直接启动旧程序；新版本升级过 → 用补丁前的完整备份恢复再启动（之后的写入不在库里，原数据目录另存为 `data.before-restore-时间`，要时人工补录，所有人重新登录）；判断不了（读不出版本、找不到备份、停服务失败）→ 服务保持停止，照打印的步骤手动恢复，不要直接启动旧程序。

## 整包

1. 备份（`npm.cmd run backup` 或 `erp.sh backup`），停止服务。
2. 新版本解压到新目录（Windows 把旧目录的 `data\`、`backups\` 复制过去；Linux 替换 `/opt/yongle-carton-erp`，数据目录不动）。
3. 启动。结构有变时启动先拍升级前快照，再在一个事务里按编号逐步升级，失败整体退回、数据不动，启动窗口写明原因；配置库同样，升级前备份在各库旁边的 `snapshots/`。
4. 退回旧版本：停服务、换回旧程序，先换回配置库（Linux `erp.sh revert-config-upgrades`；Windows 在旧目录的维护命令行手动运行 `npm.cmd run revert-config-upgrades`——旧目录的 `data\` 没动过，但 AI 设置、机器人设置在新旧共用的 `%LOCALAPPDATA%\ZhixuERP\`，不换回旧程序打不开），再看业务库：结构版本变了就用第 1 步的备份恢复。旧程序没有这条命令时照上面“转人工”做。影响同补丁回滚。

## 0.9.0 以前的旧数据

0.9.0 起业务库从空库开始（建表定为第 20 版）：**0.9.0 以前的业务库和备份不能升级或恢复；从 0.8.x 升只能整包，不能打补丁**（打了会因旧库启动失败、自动换回旧文件）。

- **碰到旧业务库：** 拒绝启动（“这是 0.9.0 以前的旧业务数据库”），旧库不动，提示写明移走哪几样。先用 0.8.4 做一次完整备份另存别的磁盘（以后只有 0.8.4 能恢复），再在业务库目录（本机安装目录的 `data/`，服务器 `/var/lib/yongle-carton-erp/data/`）把这三样**移走保存、不要删**：`erp.sqlite`（连同 `-wal`、`-shm`）、`import-archive/`、`ai-imports/`（识别工作区按编号引用客户产品，接不上新库）。再启动建空库，然后建管理员和各账号，在“设置 → API 配置”重填 DeepSeek 密钥、“设置 → 消息接入”重填机器人的应用编号和 Secret。
- **旧配置库：** 账号、AI 设置、提示词、助手工具设置认出是 0.8.4 的就整个删掉重建（`server/core/backup/versioned-sqlite.ts`）；机器人设置在配置目录 `bots/bots.sqlite`，旧位置不再读。提示词、助手工具开关、单据模板、财务科目和凭证模板都回到默认。
- **可删的旧文件：** 配置目录的 `wecom/`；数据目录 `ai-prompts/` 里的 `shipping-marks.sqlite`、`purchase-orders.sqlite`、`customer-deliveries.sqlite`。
- **退回 0.8.4：** 停掉新程序、换回 0.8.4，用 0.8.4 做的完整备份恢复（配置库已重建，只放回移走的三样不够）。0.9.0 以后录的数据带不回去。
