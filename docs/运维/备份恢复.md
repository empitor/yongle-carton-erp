# 备份恢复

什么时候读：备份、恢复、换回配置库、处理快照和升级前备份、看每日清理。

## 备份和恢复

| 类型 | 说明 |
|---|---|
| 手动完整备份 | `npm.cmd run backup`，生成 `backups/full-时间/`，运行中可以做；唯一的手动备份命令 |
| 自动备份 | 服务运行时每天一次，`backups/auto-时间/`，留最近 14 份；失败时今日页提示 |
| 删除前快照 | 删除、初始化、本机管理员直接改订单前自动拍，`data/snapshots/`，拍不成就停止操作。24 小时内全留，更早留 20 份。只含业务库，不含原件 |
| 升级前快照 | 业务库要升级时拍，`data/snapshots/upgrade-v旧版-to-v新版-时间.sqlite`，留最近 3 份 |
| 配置库升级前备份 | 配置库要升级时做，在库旁边的 `snapshots/`（如 `data/security/snapshots/`、配置目录的 `ai/snapshots/`），起名和留几份相关的见 `docs/架构/数据库升级.md`；账号库的不带会话。补丁回滚换回配置库时用；确认不再退回旧程序后可手动删 |
| 换下来的配置库 | 换回配置库时换下来的那份，在同一个 `snapshots/` 下（起名相关的见 `docs/架构/数据库升级.md`；手动换回的叫 `-before-revert-manual-时间`，可能带 `-wal` 等）。里面是新程序运行期间的配置，账号库已去掉会话。不自动清理，补录完可删 |
| 升级没做完留下的备份 | 某一步升级自己结束了事务（程序问题）、库成半截时，这次的升级前备份改名留在 `snapshots/`（名字里带 `-before-unfinished-`，相关的见 `docs/架构/数据库升级.md`）。不自动清理；**有它这个库以后都打不开**。处理：停程序，把它移到库文件的位置覆盖半截的库（附属的 `-journal` 等一起删），换上修好的或旧版程序启动 |

Linux 上的维护命令：

```sh
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh backup
sudo systemctl stop yongle-carton-erp
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh restore /absolute/backup-directory
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh reset-password 用户名
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh revert-config-upgrades [补丁开始时间]
```

- **换回配置库：** `revert-config-upgrades`（Windows `npm.cmd run revert-config-upgrades -- [时间]`），先停服务；补丁回滚和整包退回时用（相关的见 `docs/运维/升级.md`）。把比当前程序新的配置库换回从当前版本升上去时的升级前备份；给了时间（如 `2026-11-21T10:00:00.000Z`）只用这之后做的。逐个打印换回了哪个库、用的哪份备份、换下来的文件在哪，换回账号库会提示所有人重新登录；没有要换的打印“没有比当前程序新的配置库，不用换回。”。换不回的逐个打印原因、那个库不动、退出码 1（补丁回滚时就转人工）。换不回的原因相关的见 `docs/架构/数据库升级.md`，按原因处理：
  - 找不到那份升级前备份：确认程序版本对不对，或到 `snapshots/` 找合适的备份手动换。
  - 库旁边有附属文件（上次没正常关，可能有没写完的改动）：确认服务已停，照 `docs/运维/升级.md`“转人工”的做法换；拿不准交给维护人员。
  - 默认位置算不出来：多半是 `ERP_CONFIG_DIR` 不是绝对路径，改成和服务同一个绝对路径，用和服务同一套设置再运行。
- **备份里有：** 业务库、账号、AI 工作区和原件、归档、提示词、助手工具设置、出错记录，以及加密的 AI 配置和机器人配置（在 `_extra/`，机器人的叫 `bots.sqlite`）。清单 `manifest.json` 记程序版本、业务库结构版本和各配置库版本。
- **不要直接复制 `erp.sqlite` 当备份：** 运行中是 WAL 模式，复制出来可能缺最近的写入，恢复时会被拒。
- **恢复：** 先停服务，再 `npm.cmd run restore -- "备份目录绝对路径"`，用和服务同一套 `DB_PATH`、`ERP_CONFIG_DIR`。恢复前的 `data/` 另存为 `data.before-restore-时间`，中途失败自动退回。也收单个业务库文件（备份里的 `erp.sqlite` 或 `data/snapshots/` 下的快照），只恢复业务库。
- **恢复前全部校验：** 清单、sha256、每个库都过了才动数据，一个不过整份拒绝。拒绝：WAL 模式的副本（旧格式备份、直接复制的库）、0.9.0 以前的业务库和配置库、比程序新的、版本记录不完整的、不是本系统的、结构被改过的。配置库比程序旧但在 0.9.0 以后的照常恢复，启动时升级。`_extra/` 里的 AI 和机器人配置不覆盖本机、不论版本只查完整性；认不出是哪个配置库的文件也只查完整性，恢复完列出这些“只查了完整性的文件”。
- 业务库比程序新（如补丁回滚后）也能备份，清单标 `newerSchema`，只能用支持该版本的程序恢复。
- **离机保存：** 定期把备份复制到别的磁盘（服务器上另一个目录不算，要挂载或传出去），定期做一次隔离的恢复演练。

## 每日清理

怎么建、代码在哪相关的见 `docs/架构/数据库升级.md`。

服务启动 5 分钟后第一次跑，之后每小时看一次、满 24 小时才再清，库正忙就等下个小时；清了东西日志写一行“每日清理：……”。

- 防重复提交记录留 90 天。
- 订货单、送货单导出的文件内容留 180 天，之后只删文件，记录、单号、交付状态留着。
- 收件箱待处理、已忽略的消息 180 天后连附件删，已处理的（含转成单据的）留着。
- 删数据空出的空间还给磁盘（库大时稍慢）。
- 连续运行满 24 小时和关闭时更新一次查询统计。

## 代码在哪

SQLite 只读连接与一致副本在 `server/core/storage/sqlite/`，供业务库结构检查、升级、快照及配置库备份共用。

`server/core/backup/backup.ts`：每个数据库用在线备份复制成单个文件；恢复前核哈希、读文件头、校验结构。每日自动备份和失败提示在 `backup-auto.ts`；业务库以外另存进 `_extra/` 的本机配置（AI 设置、机器人设置）清单在 `server/backup-extras.ts`。配置库的恢复检查和打开时用同一个版本分类（`checkVersionedSqlite`）：登记过位置的，比程序新、比基线旧的拒绝，之间的放行（恢复后打开时升级）；`_extra/` 和认不出的位置只查完整性，恢复结果的 `integrityOnly` 列出这些文件。删除前快照、两种升级前备份都用 `consistentCopy` 做一致的副本。
