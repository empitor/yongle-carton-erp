## 2. 目标数据流

```text
Excel / 自然语言请求
       ↓
本地文件校验、保存原件、确定性解析（不执行公式/宏/外链）
       ↓
标准化工作表、表头、单元格、单位和日期，并保留来源坐标
       ↓
固定模板直接映射；有歧义时，按授权范围取样交给 Provider
       ↓
AI 返回映射和匹配建议（不接触数据库连接、SQL、源码或密钥）
       ↓
ERP 后端验证、查询匹配、建立关联、生成带版本的实际变更预览
       ↓
用户修正不确定项，并审核“新增 / 更新 / 忽略 / 冲突 / 错误”
       ↓
绑定文件哈希、计划版本、权限范围和完整差异的确认记录
       ↓
执行时再验权限、引用、金额、版本和幂等键
       ↓
单批数据库事务：客户 → 产品 → 订单 + 来源映射 + 审计
       ↓
结果报告、必要的有条件撤回 / 恢复
```

“允许把数据交给第三方模型分析”和“允许把修改写入 ERP”是两个独立授权。用户审核写入不能代替隐私授权，模型给出的 `approved` 标记也不是用户确认。

## 3. 元数据和业务接口如何扩展

目录按模块描述输入 JSON Schema、字段说明、数据库映射、计量单位、隐私分类、关联关系、匹配规则和后端业务规则。现有 `customers`、`products`、`orders`、`order_lines` 业务表均已覆盖；`schema_migrations` 作为程序维护表单独标记禁止 AI 操作。

输入结构直接由 `shared/domain.ts` 的 Zod 定义导出，避免再手写一套校验。字段语义与业务规则需要开发者随功能一起维护，并通过测试检查实际表字段覆盖。每次新增模块/修改含义时更新目录版本；已审核计划记录该版本，版本变化后重新预览与审核。

当前操作名为 `{模块}.list / create / update`，仅客户、产品、订单有已实现的人工 HTTP 接口；订单明细必须随整单保存。`totalCents` 等派生字段和系统 ID 不开放给 AI 赋值。金额由后端重算，引用必须真实存在，乐观锁版本须匹配。

以后逐步为查询增加服务层的定型筛选与字段投影，不提供任意 WHERE、JOIN、SQL 或脚本接口。用户能看到和修改哪些记录/字段，模型只能获得同样或更小范围。权限来自当前会话，后台任务也须绑定操作者并在执行时重新验证。

| 后续模块 | 规范操作方向（未实现）      | 业务限制                                             |
| -------- | --------------------------- | ---------------------------------------------------- |
| 库存     | 查询、入库、出库、调整单    | 通过变动台账计算余额，禁止直接改余额                 |
| 采购     | 查询、采购草稿新增/修改     | 供应商 → 采购单 → 明细 → 入库关系校验                |
| 财务     | 应收查询、收款草稿新增/修改 | 先只支持草稿；过账、核销、冲销需独立规则、审核和权限 |

这些模块在目录中放在 `plannedModules`，不列为可执行工具。模块上线时再实现 Schema、服务、权限、审计、元数据和测试，不提前创建空业务表或占位写入接口。

## 4. Excel 最小可用版本

### 4.1 文件与解析

- 第一版只收 `.xlsx`；根据文件内容验证 OOXML/ZIP 结构，不只检查后缀。拒绝宏文件、加密文件、旧 `.xls`、损坏文件及超限文件，后续有需求再扩展。
- 初始限制拟定为压缩文件 10 MB、解压数据 100 MB、20 张工作表、5 万单元格；单次批准写入最多 500 项。限值要用真实虚构样本压测后确定，不宣称目前已实现。
- 解析设置超时、解压比/条目数/内存边界。原件保存到服务端非公开目录，不放进 `dist/`；用随机文件 ID，不能用原文件名拼接磁盘路径。上传路由将单独限定 multipart，不能放开所有 API 的 JSON/来源检查。
- 列出每个工作表、隐藏行/列、合并单元格和候选表头；多层表头和说明行保留来源坐标。用户选择真正的数据范围，不静默忽略整张表。
- 不执行公式、宏、外部连接或链接。公式缓存值只能作为有来源的候选，缓存缺失或不可靠则待确认，不能自行重算财务值。
- 显式处理 Excel 1900/1904 日期系统、序列日期、文本日期和小数精度。`03/04`、未知币种、未知尺寸单位或含税口径不明时标为待确认。
- 联系方式和编号按文本保留前导零；金额用十进制规则转为整数分；超过当前两位单价精度时拒绝/待确认，不能静默四舍五入。
- Excel 原始空白、明确清空和未映射列分开处理。更新时空白默认不清空已有数据；清空必须有明确操作和预览。

### 4.2 确定性程序优先

已审核固定模板按“模板版本 + 表头/结构指纹 + 映射规则”直接解析，整条路径可不调用 AI。首次遇到不统一表头、多个候选字段、复杂表头或歧义时，AI 仅提出映射与解释，用户核对后可保存模板。模板更改、单位变化或新增未知列需要重审。

原文件和单元格是事实来源；模型不能发明缺失联系人、配纸、交期、成本或客户身份。必须展示建议所依据的工作表和行号，执行器从已保存的源数据重新构建变更，不能只相信模型给出的金额或“已匹配”结论。

### 4.3 跨模块关联和重复检测

- 客户先用内部 ID、已确认的来源映射匹配，再结合名称、联系方式、地址给候选；现有名称不唯一，近似名称只作提示。
- 产品需联合尺寸、材质/配纸、楞型、加工要求和未来客户产品编码；尺寸相同不意味着产品相同。内外径和箱型未确认时不推断。
- 订单优先用 ERP 编号或“来源系统 + 客户 + 外部订单号”。多行属于一单的分组键必须明确，不能把每一行都当成订单，或把不同订单按日期合并。
- 暂存计划可以用 `planned key` 引用本批次拟新增客户和产品；后端确认依赖类型、无环、没有未解决冲突，再按依赖顺序建立真正数据库 ID。
- 文件 SHA-256 识别字节完全相同的上传。另保存“解析/模板版本 + 标准化内容 + 来源范围”的指纹，发现改文件名、排版或日期格式后内容相同的候选。
- 业务幂等键/来源编号映射负责最终防重；相同内容哈希不能证明是同一张业务订单，合法重复下单不能被静默忽略。新增/更新模式必须明确。
- 更新读取当前版本和完整差异；自预览之后被其他页面改过，整批拒绝并重新生成预览，不自动覆盖新数据。
- 已匹配的客户/产品等关联记录同样保存预览时版本；关联记录变化可能影响快照或规则，执行前也应重新验证。

### 4.4 预览、确认、执行与失败

预览分页显示所有记录，支持逐项查看来源、关联匹配、修改前后值、原因和问题。新增、更新、忽略、冲突、错误五类均有数量和明细；关联客户/产品的新增也在同一预览中，不暗中创建依赖记录。

模型建议不是执行计划。本轮契约允许不完整建议，以便表达不确定字段；通过结构校验只代表格式合法，仍需后端校验必填项、实际目标、引用、金额、版本及权限，才能生成实际预览。

批准记录绑定：操作者、来源文件哈希、标准化数据/模板/业务目录版本、计划修订号、完整差异摘要、选中操作集合、有效期。修改映射、修正任何值、更换供应商结果、排除记录或修改依赖都会生成新修订并使旧批准失效。

默认一批全成功或全回滚。用户若选择忽略有问题的记录，应先生成一份依赖完整的新计划再确认；执行中不能悄悄“成功几行算几行”。在事务内重新校验引用和版本，将业务变更、外部编号映射和成功审计一起提交。SQLite 当前整单保存使用 savepoint，可嵌入未来外层事务；网络模型分析、用户等待和文件解析都在事务外完成。

提交使用持久幂等键和唯一约束。双击、断线重试或进程重启返回同一批次结果，不能再次新增。失败时业务变更回滚，失败原因和执行尝试单独保留；超时/拒答/输出截断不会生成可执行计划。

### 4.5 计划新增的持久记录（本轮未建表）

| 记录                    | 保存内容                                                                       |
| ----------------------- | ------------------------------------------------------------------------------ |
| `import_files`          | 文件 ID、原名、文件哈希、保存位置、大小、上传人、上传时间、保留策略            |
| `import_jobs`           | 来源/模板、状态、解析结果、版本、模型配置标识、操作者；不记密钥                |
| `import_plan_revisions` | 规范化输入摘要、映射、候选、差异、未决问题、业务目录版本与摘要                 |
| `import_approvals`      | 确认人、修订号/摘要、批准范围、时间与有效期                                    |
| `import_executions`     | 幂等键、执行结果、错误、各类数量、备份引用                                     |
| `import_source_links`   | 来源系统/客户/外部编号与内部记录 ID 的唯一映射                                 |
| `audit_events`          | 批次、文件/工作表/来源行、操作者、时间、操作类型、完整前后快照、版本与字段差异 |

文件和日志保留期在真实使用前由工厂确认；按权限访问，避免将手机号、地址和原始模型请求全文写入一般运行日志。原件可校验完整性；日志写权限与业务写权限分开。单机数据库日志仍不是防管理员篡改的审计保证，需要时增加异地追加存储。

恢复分成两种：执行失败的事务回滚，以及执行成功后的有条件撤回。后者须验证当前版本、后续引用和操作权限，再走业务接口执行补偿；不能把旧快照直接覆盖回数据库。新增客户/产品的归档、订单取消等撤回语义必须在启用导入前定义；当前没有这些归档操作，不能声称支持一键撤销。财务过账后只能按确认的冲销流程处理。

全库备份用于灾难恢复，会影响备份之后的全部数据，不能替代逐批撤回。未来大批写入前生成一致性备份；定期离线/异地备份并演练，注意密钥恢复与数据恢复必须都可完成。

## 5. Provider 适配与密钥管理

统一入口为 `AiProvider.analyze()`，输入为业务目录和经过权限/隐私过滤的标准化样本，输出为统一 `ProviderReply`，再经 `validateProviderReply()` 和导入契约校验。当前仅定义接口，未实现任何供应商适配器，也未发出模型请求。

| 适配器     | 计划处理的差异                                                                 |
| ---------- | ------------------------------------------------------------------------------ |
| OpenAI     | 独立处理原生结构化输出/工具参数、拒答、输出未完成和 Schema 子集                |
| Gemini     | 转换其请求/响应格式和支持的 Schema；不复用 OpenAI 请求体                       |
| Anthropic  | 转换结构化输出/工具使用与完成原因；不假设字段名兼容                            |
| 兼容第三方 | 按经验证的协议配置，不能只凭“兼容 OpenAI”认定结构化输出或工具调用可用          |
| Ollama     | 按实际本地模型能力探测并验证，区分本地服务和云端服务；性能和识别效果用样本验收 |

能力按“供应商 + 具体模型 + 端点 + API 版本”确认，包含结构化输出模式、工具调用、上下文与输出预算。内部 Schema 可以较完整，由各适配器转换为供应商支持子集；业务校验仍由 ERP 执行。没有原生 Schema 的模型可返回严格 JSON 建议并经过有限重试；持续失败转人工，不降低校验标准。

MVP 不要求模型使用工具调用：后端先做受控候选查询，模型只做分析；以后自然语言跨模块查询再加有权限的工具白名单。查询与建议不代表获得写入权。

配置页面以后保存供应商、端点、模型、能力配置和密钥引用，仅管理员可修改。密钥输入走后端，前端只看到已配置状态或掩码，不放 localStorage、不打包进 JS、不提交仓库。Windows 单机可评估 DPAPI/系统凭据存储；服务器采用专门密钥管理或分离主密钥的加密存储。不能把解密主密钥与加密密钥数据放在同一数据库/备份里。主密钥丢失可能无法恢复，投产前定义恢复与轮换方式。

端点配置本身也需后端限制：远程使用 HTTPS 和受控域名，禁止任意协议/重定向/内网探测；本地 Ollama 端点作为管理员明确配置的例外进行校验。不得因为配置字符串自称 local 就认为数据未出机。设置连接/总超时、输出大小、重试次数和费用预算，取消操作可中断分析；不因供应商失败自动把相同经营数据转发给另一个未获授权供应商。

官方资料核对依据（2026-10-24）：[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Gemini Structured Outputs](https://ai.google.dev/gemini-api/docs/structured-output)、[Claude Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)、[Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)。供应商能力仍须在实现具体适配器时重新核对，不能把格式符合 Schema 等同于业务内容正确。

## 6. 安全与隐私上线条件

- 模型无数据库连接、任意 SQL、终端、源码编辑、Schema 修改或规则修改工具；业务说明只能随代码评审和发布更新。
- 不能仅靠提示词防范恶意 Excel。工作表名、表头、单元格、备注、公式缓存和模型输出均是不可信数据；后端白名单、权限、Schema、版本、事务和审核共同限定实际效果。
- React 按文本呈现单元格，不把内容当 HTML、URL 指令或代码。以后导出表格要处理公式注入风险，同时保留原始文件供审计。
- 跨模块导入所需权限取并集，例如新增客户 + 新增产品 + 新增订单 + 批量导入；执行不得使用超出操作者范围的后台超级账号。字段级改价、财务草稿等权限另行控制。
- 每次模型分析只发送必要表头、脱敏样本及经过权限过滤的少量候选；默认不上传完整数据库或原始文件。隐藏工作表和无关列不因“上传了文件”自动获准外发。
- 开启外部供应商前审查数据项、用途、保存期限、日志/训练政策、部署地区、第三方兼容服务实际经营方和工厂授权。政策不明或不能接受时用确定性导入/本地方案；本地模型也需检查模型服务、日志、遥测和备份边界。
- AI 接口启用前完成登录、权限、审批摘要绑定、审计、来源追溯、幂等与恢复演练。未完成则只允许开发环境的模拟数据预览，不启用实际批量写入。

## 7. 开发阶段与验收门槛

| 阶段                     | 实施内容                                                                            | 可验收结果                                                              |
| ------------------------ | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 当前 A0：架构准备        | 本文、业务元数据、统一写入服务、建议契约和 Provider 接口                            | 基础功能回归通过；AI/导入写入默认拒绝；不改业务表、不联网调用模型       |
| A1：基础 ERP 验收        | 你验收客户/产品/订单，确定单位、精度、税费、订单身份、典型成本规则                  | 典型订单可核对；先解决实际业务问题                                      |
| A2：确定性导入预览       | 用虚构脱敏 `.xlsx` 样本实现上传、解析、表头映射、来源坐标、人工匹配、五类完整预览   | 不调用 AI 也能预览固定模板；歧义不猜测、文件安全限制可测                |
| A3：写入前置条件         | 登录权限、来源编号、审批、审计、幂等、批次事务、归档/取消与恢复机制；确定性导入执行 | 预览修改后旧确认失效；并发、重试、故障注入无重复/半批写入；恢复演练通过 |
| A4：AI 导入 MVP          | 选择一个获准 Provider 接入，对不统一模板做映射/候选分析；复用 A2/A3 的预览和执行    | Excel 跨客户→产品→订单导入，已授权后执行；拒答/截断/恶意内容安全退出    |
| A5：供应商与自然语言扩展 | 按需求接入其他 Provider；受控自然语言查询与修改建议                                 | 同一虚构验收集在不同模型下遵守相同规则，权限和审批不变                  |
| A6：新业务模块           | 随库存、采购、财务上线同步扩展目录、服务和测试                                      | 没有业务模块先不开放 AI 操作；财务草稿与过账权限区分                    |

阶段顺序是依赖关系，不代表所有基础 ERP 功能要等到 A4 再继续。成本、查询、生产等按工厂实际优先级推进；AI 工作可以分小步穿插，不能推翻基础流程。

AI MVP 验收集至少包括：固定模板免模型导入、陌生列名、多个工作表、同名客户、同尺寸不同配纸、同单多明细、缺少外部订单号、合法重复下单、重复上传、改名后重传、日期系统/单位歧义、公式/恶意指令、部分权限、预览后被改、双击/断网/崩溃重试、批次中途失败、模型拒答/截断和撤回遇到后续引用。验收样本先使用虚构或经你确认脱敏的数据。

## 8. 目前不应承诺的能力

1. 元数据帮助模型理解业务，但不能保证模型“完全理解整个系统”或零错误。业务目录 + 确定性规则 + 用户审核可提供可验证的替代方案。
2. 任意 Excel 的格式、业务语义和缺失信息不能都自动恢复。无法确认时必须指出需要你补充的字段；可将常见格式固化为免模型模板。
3. 文件哈希、模糊匹配和高置信度都不能独立证明业务身份。可靠更新依赖明确来源编号映射及版本检查。
4. 跨供应商协议、Schema 子集和模型能力不同，只保证内部契约统一，不承诺一次实现即可无差别切换所有模型。
5. SQLite 可继续承担单机小批量事务；大表查询、多用户写入或大批次耗时超过可接受范围时，用压测证据决定数据库分页/任务调度及 PostgreSQL 迁移，不提前引入复杂设施。
6. 一键撤回不能无条件抹除已经发生的生产、发货或财务事实。后续引用存在时应阻止撤回或走显式补偿/冲销。
