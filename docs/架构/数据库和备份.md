# 数据库结构版本

业务库和配置库怎么认版本、怎么升级，备份恢复、编号、每日清理的机制。改结构时一起改哪些地方见 `AGENTS.md`“新增功能时一起改”；各库的表和当前版本见[数据模型](../数据模型.md)；备份、恢复、升级的操作见[部署与运维](../部署与运维.md)。

## 业务库

- **代码：** `server/core/schema/`：`tables/`（当前完整结构，按表的主人分文件）、`create.ts`（空库一次建好）、`steps.ts`（升级步骤，写法和数据样例的规矩在文件开头）、`upgrade.ts`（执行升级，先拍升级前快照、只留 3 份）、`describe.ts`（结构指纹）、`index.ts`（唯一入口 `openBusinessDatabase`）。
- **认库：** 靠文件头的 `application_id`：0.9.0 以前的旧库、比程序新的、不是本系统的、版本记录缺号的一律拒绝，文件不动。版本对、表结构却和程序新建的对不上（开发时直接改了建表、被数据库工具改过）的也拒绝启动：启动时用只读连接比，升级走完提交前也比，对不上整体退回；比对在 `server/core/schema/conformity.ts`（按结构指纹，列出差在哪），恢复备份共用。
- **改结构：** 0.9.0 已发布，第 20 版是基线，快照 `tests/fixtures/schema-v20.sql` 不再改。一律在 `steps.ts` 末尾加一步，同时把 `tables/` 改成改完后的完整结构，`version.ts` 的 `SCHEMA_LATEST` 加一，数据样例放 `tests/fixtures/upgrade-samples/v<版本>.json`（自增表改名、删除另在 `tests/schema-evolution.test.ts` 的 `autoIncrementTableChanges` 登记）。再跑 `npm run schema:dump` 重新生成读库用的行结构，它写完行结构后会在导出第 20 版快照那步报错退出，这是预期的。改了表还要同步直接写 SQL 的地方：预览实例的种子 `scripts/ui-check/server.mts` 和测试里的插入语句（插入一律写列名）。
- **守着的测试：** `tests/schema-evolution.test.ts`（新建和升级上来的结构一样）、`tests/schema-constraints.test.ts`（约束）、`tests/upgrade-step-samples.test.ts`（真跑每一步核对数据）。

## 配置库

七个小库（清单见[数据模型](../数据模型.md)“其他数据库”）各用 `user_version` 记版本，和业务库一样走编号的升级步骤。规格、版本分类和登记表在 `server/core/versioned-sqlite-spec.ts`（改结构的规矩在文件开头），打开和升级在 `versioned-sqlite.ts`（`openVersionedSqlite`），升级前备份和换回在 `versioned-sqlite-backup.ts`。基础只管机制，不引用上层。

- **规格：** 每个库写明基线 `baseline`（0.9.0 发布时的版本；以后新加的库是第一次发布时的版本，定下不改）和基线以后的步骤 `steps`；当前版本 = 基线 + 步数（`latestOf`）。步骤写在规格所在的主人模块文件里，`create` 永远是当前完整结构。
- **打开时的判断顺序：**
  1. 规格写错（基线不是正整数、步骤不连续）打开前就报错，文件不动。
  2. `snapshots/` 里有这个库的 `-before-unfinished-` 备份（上次升级没做完）就拒绝，文件不动。
  3. 比基线旧（含没记版本却有表的，即 0.9.0 以前的）删掉按当前结构重建；删库只有这一支。
  4. 读写打开，读不出来拒绝。
  5. 当前版本原样打开；比程序新的拒绝；空文件在写锁里建库；基线和当前之间的：拿写锁（`BEGIN IMMEDIATE`，等不到就拒绝）→ 锁里再看一眼版本 → 做升级前备份 → 逐步执行 → 外键检查 → 提交，成功时日志写“已从第 a 版升级到第 b 版”。
  - 任何一步出错（含备份没做成、提交出错）整个退回，文件和打开前一样，提示写明哪个库、第几步、原因、备份在哪。唯一例外是步骤自己结束了事务（规矩不许）：每步后查到不在事务里就停，这一步之前的改动可能已写进文件，升级前备份改名成 `<库文件名>-before-unfinished-v旧版-to-v新版-时间.sqlite` 留下（清理和换回都认不出它），这个库就一直拒绝打开，人把它移回库文件的位置才恢复（办法在 `unfinishedAdvice`）。
  - 不在运行时核对升级后的结构（理由见规格文件开头），由测试守。
- **升级前备份：** 拿到写锁后、第一步前做，放库文件同目录的 `snapshots/`，叫 `<库文件名>-upgrade-v旧版-to-v新版-时间.sqlite`（库文件名不带 `.sqlite`，如 `users-upgrade-v1-to-v2-…`；格式定下不改，换回和回滚脚本靠它找）。账号库的去掉登录会话（`server/core/account-db.ts` 的 `clearSessions`，完整备份也用它），权限和库文件一样。同一对版本只留最新一份，最多留最近 3 对，在写锁里自己清。
- **换回：** `revertConfigUpgrades`（维护命令 `revert-config-upgrades`）把比当前程序新的库换回从当前版本升上去时的那份升级前备份，换下来的库去掉会话后留在 `snapshots/<库文件名>-before-revert-时间.sqlite`。一个库换不了只记失败、文件不动，接着换别的；换不了的有三种：找不到那份备份；旁边有 `-wal`、`-shm`、`-journal`（上次没正常关）；默认位置算不出来（`registeredHomes` 的 `unresolved`）。有失败时退出码 1，补丁回滚据此转人工。人怎么处理见[部署与运维](../部署与运维.md#备份和恢复)“换回配置库”，补丁回滚怎么用见[部署与运维](../部署与运维.md#补丁小版本)。
- **守卫：** 每个库的基线结构存快照 `tests/fixtures/config-db/<短名>-v<基线>.sql`（短名只在 `scripts/config-db-dump.ts` 定义，`npm run schema:dump` 导出，定下不改）；`tests/config-db-evolution.test.ts` 核对快照 sha256、步骤不缺、没有 AUTOINCREMENT、从快照升上来和新建的一样；`tests/upgrade-step-samples.test.ts` 真跑每一步核对数据样例（`tests/fixtures/upgrade-samples/<短名>/v<版本>.json`）；机制在 `tests/versioned-sqlite*.test.ts`。改了规格跑 `npm run schema:dump` 重新生成行结构 `server/core/schema/rows/config-db.ts`。
- **登记位置：** 主人模块加载时用 `registerVersionedSqlite` 登记默认位置，恢复备份和换回都靠它认库；新加配置库还要确认 `server/maintenance.ts` 的 `loadConfigOwners` 加载了主人模块，在 `tests/backup-create.test.ts` 的登记测试补一行。

## 备份恢复

`server/core/backup.ts`：每个数据库用在线备份复制成单个文件，恢复前核哈希、读文件头、校验结构（不打开文件看是不是 WAL 模式在 `backup-check.ts`）；每日自动备份和失败提示在 `backup-auto.ts`；业务库以外另存进 `_extra/` 的本机配置（AI 设置、机器人设置）清单在 `server/backup-extras.ts`。配置库的恢复检查和打开时用同一个版本分类（`checkVersionedSqlite`）：登记过位置的，比程序新、比基线旧的拒绝，基线和当前之间的放行（恢复后打开时升级）；`_extra/` 和认不出的位置只查完整性，恢复结果的 `integrityOnly` 列出这些文件。删除前快照、两种升级前备份都用 `server/core/sqlite-copy.ts` 的 `consistentCopy` 做一致的副本。

## 编号和每日清理

- **编号：** 被引用、会被删的表用自增编号，删掉的不复用；单号里的序号就是写事务里 `server/core/ids.ts` 的 `nextAutoId` 取到的编号。按天的流水号（合并订货单号）走 `server/core/sequences.ts`：预览只看（`peekSequence`），落库时占（`takeSequence`）。
- **每日清理：** `server/core/cleanup.ts` 的 `scheduleDailyCleanup` 满 24 小时清一次：过期的防重复提交记录、导出文件内容、待处理和已忽略的收件箱消息、业务库空闲页（各项由 `server/index.ts` 传入）；库正开着事务时整轮跳过。各项留多久见[部署与运维](../部署与运维.md)“每日清理”。
