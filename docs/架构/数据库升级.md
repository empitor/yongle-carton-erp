# 数据库升级

什么时候读：改业务库结构、配置库规格或升级步骤之前读，库打不开、升级报错要查原因时也读：业务库和配置库怎么认版本、怎么升级，编号怎么取，每日清理怎么建。

各库的表和当前版本见 `docs/生成/表结构.md`；改结构要一起改的相关的见技能 `.claude/skills/schema-change/`；备份、恢复、升级的操作相关的见 `docs/运维/备份恢复.md`、`docs/运维/升级.md`。

## 业务库

- **代码：** `server/core/schema/`：`tables/` 当前完整结构（按表的主人分文件）、`create.ts` 空库一次建好、`steps.ts` 升级步骤（写步骤的规矩在文件开头）、`upgrade.ts` 执行升级（先拍升级前快照、只留 3 份）、`describe.ts` 结构指纹、`index.ts` 唯一入口 `openBusinessDatabase`。
- **认库：** 靠文件头的 `application_id`。0.9.0 以前的旧库、比程序新的、不是本系统的、版本记录缺号的一律拒绝，文件不动。版本对、表结构却和程序新建的对不上（直接改了建表、被数据库工具改过）也拒绝启动：启动时用只读连接比，升级走完提交前也比，对不上整体退回。比对在 `server/core/schema/conformity.ts`（按结构指纹，列出差在哪），恢复备份共用。
- **第 24 步：** 在升级事务内重建订单头和明细，回填税费三列并恢复索引。旧口径先去首尾空白再认，“不含税”归“未税”；认不出的口径逐字接在税率原话后面，另起一行加“口径：”，程序从“口径：”那一行读到末尾。同一步转换订单状态操作的重试结果，保留请求号和原摘要。升级样例核对 SQL 与 `readTaxRate` 的认法，历史送货单和财务记录原样保留。
- **第 25 步：** 新建 `customer_sites`。比较和回填前三项（地址、联系人、联系方式）都去首尾空白（含全角空格），名字、上限、空白清单在步骤里写成字面量。
  - 老客户（含已归档）三项至少一项有内容的，按档案回填“默认厂区”。
  - 没挂厂区的待送货单（含已归档的）挂上厂区：三项和档案一样的挂默认厂区；不一样的按单上三项给客户补建厂区，同一客户三项相同的几张共用一个。客户本来没有厂区时编号最小那组叫“默认厂区”并当默认，其余叫“送货单 <单号> 的地址”（单号取组里编号最小那张的），建单时间取那张单的。
  - 三项全空、超出厂区录入上限（联系人 60、联系方式 50、地址 300，按 JS 字符串长度，带 NUL 的算超长）、客户已不在的不挂。
  - 已出库、已取消、已撤销的送货单一字不动；挂上的只在单据内容末尾加 `siteId`、`siteName`，版本号和更新时间不变，不写审计。

## 配置库

七个小库（清单见 `docs/生成/表结构.md`）各用 `user_version` 记版本，也走编号的升级步骤。规格和登记表在 `server/core/backup/versioned-sqlite-spec.ts`（改结构的规矩在文件开头），打开和升级在 `server/core/backup/versioned-sqlite.ts`，升级前备份和换回在 `server/core/backup/versioned-sqlite-backup.ts`。基础只管机制，不引用上层。

- **规格：** 每个库写明基线 `baseline`（0.9.0 发布时的版本；以后新加的库是第一次发布时的版本，定下不改）和基线以后的步骤 `steps`；当前版本 = 基线 + 步数。步骤写在规格所在的主人模块文件里，`create` 永远是当前完整结构。
- **打开时的判断顺序：**
  1. 规格写错（基线不是正整数、步骤不连续）打开前就报错，文件不动。
  2. `snapshots/` 里有这个库的 `-before-unfinished-` 备份（上次升级没做完）就拒绝，文件不动。
  3. 比基线旧（含没记版本却有表的）删掉按当前结构重建；删库只有这一支。
  4. 读写打开，读不出来拒绝。
  5. 当前版本原样打开；比程序新的拒绝；空文件在写锁里建库；基线和当前之间的：拿写锁（`BEGIN IMMEDIATE`，等不到就拒绝）→ 锁里再看一眼版本 → 做升级前备份 → 逐步执行 → 外键检查 → 提交，日志写“已从第 a 版升级到第 b 版”。
  - 任何一步出错（含备份没做成、提交出错）整个退回，文件和打开前一样，提示写明哪个库、第几步、原因、备份在哪。唯一例外是步骤自己结束了事务（规矩不许）：每步后查到不在事务里就停，升级前备份改名成 `<库文件名>-before-unfinished-v旧版-to-v新版-时间.sqlite` 留下，这个库一直拒绝打开，人把它移回库文件的位置才恢复（办法在 `unfinishedAdvice`）。
  - 不在运行时核对升级后的结构，由测试守。
- **升级前备份：** 拿到写锁后、第一步前做，放库文件同目录的 `snapshots/`，叫 `<库文件名>-upgrade-v旧版-to-v新版-时间.sqlite`（库文件名不带 `.sqlite`；格式定下不改，换回和回滚脚本靠它找）。同一对版本只留最新一份，最多留最近 3 对。
- **换回：** 维护命令 `revert-config-upgrades`（`revertConfigUpgrades`）把比当前程序新的库换回从当前版本升上去时的那份升级前备份，换下来的库去掉会话后留在 `snapshots/<库文件名>-before-revert-时间.sqlite`。一个库换不了只记失败、文件不动，接着换别的。换不了的三种：找不到那份备份；旁边有 `-wal`、`-shm`、`-journal`；默认位置算不出来。有失败时退出码 1，补丁回滚据此转人工。人怎么处理相关的见 `docs/运维/备份恢复.md`，补丁回滚相关的见 `docs/运维/升级.md`。
- **基线快照：** 每个库的基线结构存 `tests/fixtures/config-db/<短名>-v<基线>.sql`（短名只在 `scripts/config-db-dump.ts` 定义，`npm run schema:dump` 导出，定下不改）；`tests/core/config-db-evolution.test.ts` 核对快照 sha256、步骤不缺、没有 AUTOINCREMENT、从快照升上来和新建的一样。
- **登记位置：** 主人模块加载时用 `registerVersionedSqlite` 登记规格和默认位置。完整备份、恢复和换回都靠它认库。完整备份、升级前备份和换回时留存的副本都执行库规格上的 `scrubBackup`（如账号库去掉登录会话）。

## 编号

规则和单号格式见 `docs/架构/数据库约定.md`“约定”；单号里的序号是写事务里 `nextAutoId` 取到的编号。按天的流水号（合并订货单号）走 `server/core/storage/sequences.ts`：预览只看（`peekSequence`），落库时占（`takeSequence`）。

## 每日清理

`server/core/backup/cleanup.ts` 的 `scheduleDailyCleanup` 满 24 小时清一次：过期的防重复提交记录、导出文件内容、待处理和已忽略的收件箱消息、业务库空闲页（各项由 `server/index.ts` 传入）；库正开着事务时整轮跳过。各项留多久、运维上怎么看相关的见 `docs/运维/备份恢复.md`。
