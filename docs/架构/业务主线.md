# 业务主线

档案读写、库存流水、单据流转和订单进度、删除和初始化怎么实现。业务规则在 `AGENTS.md`“业务规则”；表和字段见[数据模型](../数据模型.md)；模块分层见[架构说明](../架构说明.md)“模块”；先预览再确认、防重复提交这些通用做法见[服务端通用做法](服务端写法.md)。

## 客户产品订单和唛头

- `server/sales/index.ts` 的 `sales(store)` 读写客户、产品和订单档案，查重也由这个模块提供。页面、数据管理和助手的保存都经订单服务。识别导入按自己的确认和事务流程新建档案。
- 产品的唛头由这个模块的 `MarkService` 保存，产品详情走 `marksRouter`，助手和业务总览共用服务。

## 库存流水和余额

- **是什么：** 余额只由 `stock_movements` 派生。流水只追加，数量是千分单位整数；更正靠冲销和替代流水；数量为 0 的只有盘点能记。
- **谁写：** 流水、库存品和采购单的版本号、采购明细只由 `server/operations/ledger/ledger.ts` 写（别的模块经 `stockLedger` 调）；删除和初始化时由 `server/operations/deletion.ts` 写，删流水时给相关库存品加版本号，看过的预览随之作废。管理员改写、删除流水留 `stock_movement_revisions`。三种 JSON 列（库存品规格、订货单到货安排、修订记录）的结构在 `shared/business/operations-stored.ts`，读写都按严格结构核对。
- **两种视图：** 基本视图（只有采购库存自己的数据，采购单已到货读缓存）在 `shared/business/operations-views.ts`，`OperationsService` 读。完整视图（采购单现算已到货、带到货记录；库存品带已安排和可用；订货单带到货单；流水带来源单号）在 `shared/business/stock-flow-views.ts`，由单据流转的 `FlowService.views` 拼。
- **保存只走一个入口：** 保存采购单、库存品，改采购单状态，手工出入库只走单据流转的 `server/flow/stock/stock-entries.ts`（`FlowService.stock`），页面、助手、数据管理、单据导出、脚本都用它。
- **同一种货一个库存品：** 撞上已有的回 409 `stock-exists`。完工按产品取成品库存（`finishedStockFor`，没有就建、归档的恢复）；到货没选库存品按查重键用已有原材料（`rawStockFor`）。查重和规格比对只用 `shared/business/stock-identity.ts`。订单服务改产品时，在同一个保存点调用采购库存的 `syncFinishedStock` 更新关联成品库存。
- **用过的库存品：** 有流水或被单据、采购明细引用的，不能改种类，成品不能改关联产品，对所有账号生效；判断只在单据流转的 `StockViews.usages`。
- **成品批次不存表：** 每笔有效的完工入库算一批，剩余按流水推算（`shared/business/stock-batches.ts`）；批次备注就是完工单的 `notes`，用说明编辑改。

## 单据流转和订单进度

- **单据：** 到货、生产任务、完工、送货单都存 `flow_documents`，只由 `server/flow/documents/document-store.ts` 写（5 个镜像列由 `flowColumns` 从 `document` 算），同时维护关联索引 `flow_refs`。
  - `document` 列是 `shared/business/flow-document.ts` 的严格结构（每种单据一份，多键、类型不对、缺必填都报错），只存单据内容，不存行上的列和派生字段。
  - 读库里的内容只经 `server/flow/documents/read.ts` 的 `storedContent`；别的服务端模块写 `parseStoredJson(flowDocumentSchema(种类), row.document, …)`。写前按同一份结构核对，不过按服务端错误报（500“保存失败，请检查服务日志后重试”）。要视图走 `FlowService.get(id, kind?)`、`list(kind)`；收视图再写回用 `viewContent`。
  - 服务端写的字段分生命周期记录（`lifecycleFields`）和抄下来的快照。快照每一项跟哪个引用登记在 `shared/business/flow-snapshot.ts`（缺一项编译不过）。重新保存单据的路径（三种更正、改已下达的任务、管理员连带的整份替换和拆单）都过 `keepSnapshot(原单, 新单)`：引用没变的留原单的，换了的按新的取（规则见[数据模型](../数据模型.md)“单据内容”）。
  - 有效只看 `status` 是 `confirmed`；`draft` 界面叫待送货、待入库。生产任务没有 `draft`，新建就是已下达（建表也拦）。核对入库、出库先预览再确认（`server/flow/rules/preview.ts`、`confirm.ts`）；前端的核对请求只有 `src/flow/flow-api.ts` 的 `previewFlow`、`confirmPreview`。
- **归档：** 单据、档案、识别文件的归档恢复只有 `server/core/archive.ts` 的 `changeArchive` 一种做法（批量、逐条事务、版本校验、审计），各处只给 `ArchiveTarget`；业务库记录用 `recordArchiveTarget(store, { load, blocked, after? })`。什么时候不能归档：单据 `server/flow/documents/archive.ts`，档案 `server/lifecycle/lifecycle.ts`，识别文件 `server/import/workspace-files.ts`。连已归档一起看要超级管理员模式。能归档、能记墓碑的记录种类由主人模块登记（`registerRecordKinds`），写前核对；加一种只要登记，不改表。
- **订单进度：** 生产中、待发货、已发货由 `server/flow/rules/order-progress.ts` 的 `updateOrders` 按有效单据重算，本机管理员改订单后也只由它重算。规则：明细全发完是已发货；有已下达的生产任务时，未发完的每个产品都做够是待发货、否则生产中；没任务但发过货是待发货；都没有是已确认。没出过库的待确认、已取消是人定的，不被覆盖；人能点的状态动作（确认、退回待确认、取消、恢复）在 `server/orders/order-status.ts`。“部分发货”不存、显示时派生。
  - `sales(store)` 的 `order`、`orders`、`ordersByIds` 返回普通 `Order`。订单服务的 `trackedOrder`、`trackOrders` 返回 `TrackedOrder`，一批订单分别查一次单据流转的 `shippedByLine` 和采购库存的 `materialByOrder`。仓库送货台账直接用 `shippedByLine`。
  - 订单算不算数、还能不能送、是不是已结束只在 `shared/core/domain.ts` 判断（`effectiveOrder`、`deliverableOrder`、`closedOrder`，SQL 用 `uncountedOrderStatuses`）；详情的状态按钮按 `shared/business/record-status.ts` 出现；下一步提示 `shared/business/order-next-step.ts`；今日页分组 `server/overview/workbench.ts` 的 `buildToday`。
- **生产任务完工了多少：** 只在 `shared/business/task-progress.ts` 算，服务端和登记完工都调它，前端只管显示。要合计的数（订单明细已发、任务已完工和待入库、待送货单占用的库存）在 SQL 里直接取那几列，不整份解析单据。
- **计划日：** 生产任务和送货单的计划日由表级 CHECK 保证；录入没给时用单据日期。
- **读单据和回答结构：** 按编号读一批用 `read.ts` 的 `storedDocuments`。单据视图、保存、排期、登记到货、批量登记完工的结果都按结构核对；只读接口的回答结构在 `shared/business/flow-views.ts`。到货记录没关联采购单的行，页面写“无采购单”。仓库台账 `GET /flow/daily` 带 `doc`（到货单、送货单编号）时只组装这一张、连已归档的（找不到或种类不对 404，生产任务被拒）；不带时不含已归档的。
- **采购已到货：** `purchase_lines.received_units` 是缓存，由 `server/flow/rules/receipt-events.ts` 按有效到货单减没冲销的退货重算，只算相关采购单。基本视图读缓存，完整视图现算。
- **登记到货：** 只有 `server/flow/arrival/register-arrival.ts` 的 `registerArrival` 一个入口（`POST /api/order-batches/:id/receive`、助手 `order_batch.receive`）：按订货单分到各条采购明细，每行可另给入库数量（不给等于合格数）；采购单还没订货单时同一事务里补建。挂采购明细的到货单只能这样存，通用保存只收不挂采购单的货。AI 识别的送货单带 `pending` 存成待入库。
- **改已生效的单据：** 已入库的到货单、已出库的送货单（含已送达）、已入库的完工单只有更正、编辑说明、撤销三条路。
  - **更正（撤销 + 替代）：** 核心 `server/flow/correction/correction.ts`：`planCorrection` 在 `rehearse` 里出预览；`correctDocument` 核对摘要后一个事务里写替代单、写流水、读回核验，原单和替代单各记一条“更正”审计。原单流水按库存品合计冲回，先记加库存的再记减库存的（`correction-movements.ts`，撤销也用它算“不够扣”）。
    - 三种单据各一份方案，核心按种类分派；输入结构在 `shared/business/flow-correction.ts`，预览视图（含库存前后）和提交结果在 `flow-correction-views.ts`。地址 `POST /api/flow/:id/correction-preview`、`/correct` 三种共用；生产任务、已归档的不能更正。
    - 替代单写 `correctionOf`，原单写 `replacedBy` 并改成 `reversed`（只由更正写）；出库日、送达记录、确认人和时间沿用原单。
    - 快照（名称、品名规格、单价税率、材质楞型、尺寸、面积金额）：替代单每行按顺序对上原单同一条订单明细（到货是同一条采购明细和库存品）的一行。
      - 照原单那行（档案后来改名也不变）：没换供应商、产品的行；换挂、新加但用原单已有订单明细的行。
      - 按档案和明细现在的取：用原单没有的订单明细，或换了供应商、产品、采购明细的行。
      - 送货金额按留下的单价乘新数量，订单现价不同时提示一句。
    - 权限：到货、送货有业务编辑权限就能更正，完工要超级管理员模式；本机管理员另能改送货的出库日期、换挂、加行，完工的日期、产品、任务。助手的更正命令在 `server/assistant/tools/corrections.ts`，预览就是卡片，确认时带同一个摘要提交。
  - **编辑说明：** `server/flow/correction/document-info.ts` 的 `updateDocumentInfo`（`POST /api/flow/:id/info`）只改表头归“说明”的栏目（`documentInfoFields`）：到货改备注、到货时间；送货改备注、收货地址、联系人、联系方式、实际时间；完工改备注（批次备注）、操作人。不进财务指纹，库存、金额不动，不出替代单。单据详情、数据管理、批次块、助手 `flow.edit_info` 共用。
  - **撤销和退货：** 整张没发生用撤销（`server/flow/rules/undo.ts`）。采购退货在 `server/flow/arrival/returns.ts`，挂在有效到货单下。
  - **数据管理改已生效的单据：** 只改说明的走 `updateDocumentInfo`，改数量、日期的回 409 指向更正；已撤销、已取消、已被替代的不能改。开工后的生产任务本机管理员用同一个 `FlowService.save` 改，计划数不能改小到已登记的完工数以下（含待核对入库，不含已取消、已撤销）。
- **送货：** 新建只有“安排送货”一个窗口（`src/warehouse/DeliveryPlanDialog.tsx`）；超订单数量要写原因、要超级管理员模式。
  - 能发哪些、同一份库存按交期先后怎么分只在 `shared/business/warehouse-delivery.ts`；排出送货单、按客户档案预填收货信息、几个客户等同一种货、送不了的原因、超订单的行只在 `shared/business/delivery-plan.ts`。安排送货窗、仓库页“可发货”、助手 `delivery.plan` 都调它们。
  - 待送货 → 导出送货单并出库（单据导出调 `FlowService.shipDelivery`，导出和交付跨零点时带上出库日），或“不导出直接出库” → 确认送达（只记送达日，不动库存）。出库那天就是单据日期，财务按它归月。
- **完工：** 登记完工只有 `server/flow/production/batch-completion.ts` 的 `ProductionCompletion` 一个入口（页面、助手共用；挂任务和不挂任务的一起登记，按产量分领料）；`POST /api/flow/production` 新建一律拒绝，数据管理也不能新建完工单。可先登记成待入库再逐张核对；每张任务还能登记的 = 计划 − 已入库 − 已登记待入库。
- **保存订单明细：** 已有编号的原地更新，没编号的新增，没再提交的原明细删除。明细按编号显示，新行排在保留行之后。新建不能带明细编号，修改时拒绝重复和不属于当前订单的编号。普通改单由订单服务把单据流转的 `orderEditGuard` 核对传给保存函数，按补齐后的明细检查已有单据的限制。
- **本机管理员改订单的连带：** `server/orders/order-edit-cascade.ts` 协调订单保存前后的操作。删除明细时，整张送货单需删除的交给删除引擎，仍有明细的交给 `server/flow/rules/order-edit-cascade.ts` 去掉相应行。订单保存后，单据流转还负责送货单换客户、拆单、生产任务解除关联。库存数量不动，流水改挂留修订记录。改单据经 `keepSnapshot` 保留引用未变的快照，拆出的新单带原单的经办记录（流水号另算，更正关系不带），换了客户时取新客户名。
- **本机管理员改库存品、采购明细的连带：** 单据的相关内容由 `server/flow/rules/maintenance-cascade.ts` 调整。

## 删除和初始化

- **一条路：** 日常是归档。物理删除只有删除归档模块的 `server/lifecycle/database-maintenance.ts`：页面 `/api/deletions/preview`、`/execute`，本机数据管理（打开同一个删除窗、发同一个地址），助手 `records.delete` 都走它。
  - 先预览影响清单，提交时核对同一范围摘要（会连带别的记录时必须带）。删前 `snapshotBeforeDestructive`（初始化也用：把业务库一致地复制到数据目录的 `snapshots/`，5 分钟内没写过就复用上一份，拍不成报 507、本次不执行），写审计和墓碑。
  - 不另拍快照的删除只有 `deleteAfterSnapshot`，要拿本库的快照凭证 `TakenSnapshot`（同一操作里已拍过快照的调用方才有，比如本机管理员改订单连带删整张送货单）。
- **谁能删（`deletionAccess`）：** 本机管理员都能删；不在本机时，还没核对的到货、完工、送货单有业务编辑权限就能删，其余要超级管理员模式加本人密码。拒绝分 401 `authentication`、403 `permission`（不是超级管理员账号）、403 `super-mode`（没进模式）。
- **规则登记：** `server/core/deletion-rules.ts`，各模块在自己的 `deletion.ts` 登记（财务只登记初始化）。删除只改业务的表，被删的来源由财务下次补扫发现（见[财务](财务.md)“来源被删”）。
  - 引擎先按外键找连带的行（能置空的置空，不能的跟着删），再跑各模块的规划规则；镜像列置空时同一句清掉 `document` 里的字段。
  - 要删、要改的表没人登记，预览就拒绝；删订单时没有模块登记“删订单前配合”（识别导入给导入记录打标记），也拒绝。
- **库存怎么处理：** 一起改回（`recalculate`），或库存不动（`preserve`：被删单据的流水改成“系统维护”流水留着，留修订记录）。叫法、选项文字只在 `shared/business/deletion-words.ts`；清单排版 `src/recordkit/deletion-impact.ts`，删除窗和助手卡片共用。
- **初始化：** `server/admin/business-reset.ts` 按 `registerReset` 登记的顺序让各模块清自己的表。客户产品订单先清唛头，单据和成品库存清完后再清档案，保留哪些表写在 `tests/business-reset.test.ts`。
