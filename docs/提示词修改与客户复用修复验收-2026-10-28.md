# 提示词修改与客户复用修复

工作区版本0.5.3，业务目录27，无业务数据库迁移。本轮不提交、不推送、不发布，不修改历史版本标签。

## 实际根因

只读检查最近真实对话，确认助手引用未展示的“上述文字”要求保存，并可能把自身规则指向订单识别预设。原系统规则明确禁止修改提示词，注册表也缺少提示词管理工具，模型只能口头确认。任务没有记录目标条目、完整方案及展示证据，无法区分拟定和批准。

批量导入的各工作区预览把客户记为new；首份正式创建客户后，后续预览仍保留new。原正式服务正确拒绝同名重复建档，但没有自动刷新匹配，导致可恢复的冲突阻断批次。旧汇总还可能保留此前失败，即使该文件后来已成功。

## 实现

- prompts.get读取原模块管理器和真实预设目录，按需读取指定预设完整条目，避免注入所有预设正文。自身规则默认assistant，与sales-order隔离；生产应用接入原有各模块实例，没有第二套存储。
- prompts.propose验证真实条目、版本、完整内容及大小，任务memory.promptEdit保留目标和全文。服务器直接展示全文并记录消息ID；润色撤销旧展示资格。用户改变明确模块时采用最新要求。
- prompts.save仅接受当前任务中最新已展示方案及其后真实用户同意。原管理器保存后重新读取核验，保留活动预设和其他条目。目标正文被他人修改时拒绝覆盖；无关修订可安全重基；中断后实际内容已生效则只核验，不重复修订。成功回执决定结束，无需模型再次索要确认。
- 统一注册表继续控制权限及启停；提示词管理复用business:edit。保存审计记录模块、条目、方案及内容哈希，不输出密钥或全文。
- customer-resolution供候选查询、助手准备与原正式导入服务共用。空白/Unicode括号差异、唯一历史订单关联可证明同一身份；去掉公司后缀仅生成候选，不直接合并公司。候选附联系信息和归档状态。
- 批次逐份刷新客户真实ID和版本。已有工作区映射、正式回执与created记录共同充当客户对应关系，未新增客户缓存表。已确认同客户关系只引用当前批次/任务的真实回执；归档客户阻断并说明恢复要求，不静默恢复。
- 每份正式订单仍经过原完整预览、权限、版本、来源、事务、审计及幂等校验；最终汇总按每份文件最新结果去掉已恢复的旧错误。

## 自动化验证

新增tests/assistant-prompt-customer.test.ts，全部使用独立临时业务库、提示词库和模型替身：

1. 讨论→先展示全文→润色后重展→“好，保存”，即使模型仍请求确认也能正确结束；订单识别提示词不受影响。
2. 未展示、同轮模型自批、旧方案、跨任务、无权限均拒绝保存；无关修订安全重基。
3. 最新模块优先；目标文字实质冲突拒绝覆盖；缺失模块和停用工具拒绝执行。
4. 重开临时业务库和提示词库，模拟写入已提交但任务回执尚未提交，恢复后读回核验且修订不重复增加。
5. 五份虚构订单，首份创建客户、后四份复用真实ID，五份正式执行台账核验，任务完成；重试不重复建档或导入，历史名称更改仍可关联。
6. 排版差异自动复用，相似公司不合并，归档客户不重复创建；部分失败只报告实际成功及剩余阻碍，不错误结束任务。

最终结果：`npm test`全部411项通过（新增6项），无失败或跳过；`npm run typecheck`通过；`npm run build`通过；`git diff --check`通过。构建保留现有Zod依赖注释及大于500KB的分包提示，不影响产物生成。首次全量检查仅两处旧目录版本断言失败，已同步为27并重新完整验证通过。

## 保留边界

没有重新导入真实订单，没有修改真实业务库，没有调用收费模型。自动化验证真实业务服务，但不代表已对在线供应商模型做实测。只有相似名称、缺乏可靠身份依据时仍须人工判断；归档客户仍需按业务流程恢复。当前提示词方案一次修改一个已有条目，需要改多条时逐条拟定与保存，未新增预设管理存储或批量提示词事务。
