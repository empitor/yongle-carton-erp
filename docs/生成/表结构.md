# 表结构

什么时候读：加表、加字段、改约束或配置库之前，查现在每张表管什么、有哪些列和约束。

由 `npm run docs:gen` 生成，不手改：业务库来自 `server/core/schema/tables/` 的建表语句和写在每句前面的注释，配置库来自各库规格的 `create`。要改说明就改那里的注释，再跑 `npm run docs:gen`；`tests/checks/docs-generated.test.ts` 核对这份是不是最新。

- “说明”栏是建表语句括号里写在列、约束前面的注释。
- 约定（STRICT、金额、编号、JSON 列）、派生关系、表归哪个模块，相关的见 `docs/架构/数据库约定.md`。

## 业务库

程序新建的业务库是第 25 版。

### 基础

业务库默认是 `data/erp.sqlite`（`DB_PATH` 可改），它所在的目录叫“数据目录”。当前结构以 `server/core/schema/tables/` 为准，
按表的主人分文件；版本是 `server/core/schema/version.ts` 的 `SCHEMA_LATEST`。第 20 版快照、升级步骤和生成的行结构相关的见技能 `.claude/skills/schema-change/`。
`sqlite_sequence` 是 SQLite 自己记自增表用过的最大编号的表，只有升级执行器（`server/core/schema/upgrade.ts`）补写。

#### `schema_migrations`（STRICT）

数据库版本记录：新库按当前结构直接建，第 20 版到当前版本各记一行；升级上来的每段升级加一行

#### `products`（STRICT）

产品（长宽高可以不填；尺寸单位只有 `mm`、`cm`，认不出的单位原文记在 `dimension_unit_raw`）。

这个算式靠 STRICT 保证列里一定是整数（整数相除才是取整）。`parent_product_id` 是“附属于哪个产品”，只管显示归组，不能附属自己。
`customer_id` 外键指 `customers`，可空：通用产品留空，填了的只给该客户下单；删客户时置空，下过单且已定客户的不能改客户。

| `version` | INTEGER | `NOT NULL DEFAULT 1 CHECK(version>=1)` |

#### `orders`（STRICT）

订单。单号唯一；客户名是快照。`total_cents` 是按明细算出来存着的合计（分）；精确到万分之一元的合计不存，读的时候按明细现算。
只收人民币（`CNY`）；规范税率存万分比整数，含税口径只收枚举值，原话另外留在 `tax_text`。
客户采购单号等可选说明从没给过是 NULL，给了空白的存空串。

订单头和明细各存 `tax_rate_bp`（0 到 10000 的整数万分比，13% 存 1300）、`tax_mode`（含税、未税、未明确）和 `tax_text`（原件或旧数据的原话）。
前两列没填或认不出时为 NULL。订单接口的 `taxRate` 是百分数数字（13 表示 13%），`taxText` 是原件写法。

#### `stock_items`（STRICT）

库存品（原材料、成品）。同一种货只有一个库存品，归档的也算：

`raw_key` 是原材料的查重键（`shared/business/operations/stock-identity.ts` 的 `rawStockKey` 算出来存这里，服务端查重用同一个函数），
名称、规格说明、尺寸、材质、楞型规范化后相同的原材料只能有一个（唯一索引）；成品不存（按产品唯一）

#### `stock_movements`（STRICT）

库存流水：只追加，余额只由它派生，前后余额不为负；`seq` 是登记顺序，永不变、删掉的也不复用。
数量是 0 的流水只有盘点（`adjust`）能记，表示盘过了、数量没变；别的出入库一律不记 0（表末尾的 CHECK）。
写流水的地方（确认、冲销、管理员编辑、拆送货单、到货更正、采购退货及冲销、批量完工、手工出入库、删除时库存不动）

### 单据流转

#### `flow_documents`（STRICT）

单据：到货单 `arrival`、生产任务 `task`、完工单 `production`、送货单 `delivery`。`status`：`draft`、`confirmed`、`cancelled`、`reversed`，
生产任务没有 `draft`；生产任务单位只有“只”；只由 `server/flow/documents/document-store.ts` 写。

单据内容（`document`）的结构以 `shared/business/flow/flow-document.ts` 的 `flowDocumentSchema`(种类) 为准：录入字段加服务端补的字段，
写和读都按它核对（多键、类型错、缺必填才报错，带默认值的缺了补上）。只存单据内容；行上的列（编号、种类、单号、状态、版本、
操作人、时间）和派生的（完工进度、实际日期）不存，种类在列上，读的时候带上。服务端补的字段分两类：生命周期记录
（确认、取消撤销、出库送达、更正关系，`lifecycleFields`）和抄下来的快照（名称、单价税率、材质楞型、尺寸、面积金额：
严格结构减去录入字段和生命周期字段）。

| 种类 | 服务端补的字段 | 谁写 |
|---|---|---|
| 四种都有 | `confirmedBy`、`confirmedAt` | 核对确认（生产任务是下达）；更正、改订单拆单沿用原单 |
| 四种都有 | movements | 核对确认、更正的替代单、改订单拆单、调整送货单；删流水时滤掉 |
| 四种都有 | cancellation、reversal（原因、人、时间；撤销另带流水，更正另带请求号） | 取消、撤销；更正时标在原单上 |
| 四种都有 | `correctionOf`、`correctionReason`、`correctedAt`；原单 `replacedBy` | 更正。删除引擎删原单时 `correctionOf` 写 null，删替代单时去掉 `replacedBy` |
| 到货 | `supplierName`、`correctionOfReceiptId` | 核对确认；更正沿用 |
| 到货明细 | area、amount、`purchaseId`、`purchaseNumber`、`supplierName`、验收三个数、新建的 `stockId` | 核对补全；改库存品时重算面积金额，解除采购明细或删采购单时清采购单 |
| 生产任务 | `productName`；`plannedDate` 必填，没写按单据日期补 | 下达 |
| 完工 | `productName`、`finishedStockId`；`taskId` 可为 null | 核对确认；删任务时置空 |
| 送货 | `customerName`、`shippedAt`、`shippedBy`、`deliveredAt`、`deliveredBy`；`plannedDate` 必填。出库后 `date` 是出库日，`plannedDate` 留原安排日 | 核对出库、确认送达；更正和拆单沿用 |
| 送货收货信息 | `siteId` 可空，`siteName`、address、contact、phone 是快照 | 保存待送货单取选中的厂区，空时取客户默认厂区；更正沿用快照；改单换客户时待送货单取新客户默认厂区，已出库、已取消、已撤销的只清 `siteId`、留着收货信息；删除历史单据引用的厂区只清 `siteId` |
| 送货明细 | `productName`、specification、unit、`orderNumber`、`externalPurchaseOrder`、`customerProductCode`、`unitPriceExact`、`amountExact`、`taxRate`、`taxMode`、material、flute、`productId`、length、width、height、`dimensionUnit` | 核对补全 |

快照怎么留：每一项跟着哪个引用登记在 `shared/business/flow/flow-snapshot.ts`（缺一项编译不过）。重新保存单据（更正、改已下达的
生产任务、管理员改订单和库存品、解除采购明细）都过 `keepSnapshot`(原单, 新单)：

1. 新单每一行按顺序对上原单一行：送货认同一条订单明细，到货认同一条采购明细和库存品；对过的不再用。
2. 对上了、引用没变的，留原单那行的快照；换了引用或改了数量、纸板资料的取新的；对不上的用新单的。
3. 送货换了引用，按留下的单价乘新数量重算金额。

所以档案改名后再更正，替代单上仍是原来的名字。待送货单保存时刷新收货信息。已出库送货单的地址、联系人和联系方式可以改，走和页面“编辑”同一个说明编辑（权限、版本、修改历史都一样）；数据管理界面上没有这几格。
待送货单占用的厂区不能删除。历史送货单解除厂区引用后保留收货信息，财务来源指纹不变。

## 配置库

配置库各是一个 SQLite 文件，用自己的 `PRAGMA user_version` 记版本：基线是 0.9.0 发布时的版本，当前版本是基线加升级步骤数。版本怎么算、规格怎么写、怎么升级，相关的见 `docs/架构/数据库升级.md`。

- **配置目录：** 配置目录在哪，相关的见 `docs/运维/部署.md`；“数据目录”是业务库所在的目录。
- **业务初始化：** 只按范围清识别工作区，别的配置库不动。
- **快照和备份：** 业务库快照、配置库升级前备份放在哪，相关的见 `docs/运维/备份恢复.md`。
