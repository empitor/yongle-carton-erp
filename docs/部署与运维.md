# 部署与运维

给维护的人看：怎么装、怎么升级、怎么备份恢复、日常怎么排查、怎么打包。程序内部的机制（结构升级、配置库、登录限频、删除快照怎么实现）见[架构说明](架构说明.md)，还没做的部署工作见[路线图](路线图.md)“公网开放”。

正式部署只用 Ubuntu 24.04 LTS x64 服务器（腾讯云），同机 Caddy 负责 HTTPS；Windows 只作本机使用。两个平台各有原生安装包，内置 Node.js 24 和原生依赖。

维护命令：Windows 在安装目录双击 `维护命令行.cmd` 后运行 `npm.cmd run …`（源码目录直接用终端）；Linux 用服务账号运行 `scripts/linux/erp.sh`，见“备份和恢复”。

## 本机（Windows）

- 启动：双击 `启动系统.cmd`，窗口保持打开（源码目录会先构建再启动）。停止：双击 `停止系统.cmd`，或在原窗口按 `Ctrl+C`。
- 地址 `http://127.0.0.1:3001`，端口用环境变量 `PORT` 改。需要 Node.js 24.15 或更高的 24.x。
- 同一个数据库只能起一个实例，由 `data/erp.sqlite.running` 锁定；异常退出留下的锁下次启动自动清理。
- 数据位置：安装目录的 `data\`（业务库、账号、AI 识别工作区和原件、提示词、日志）、`backups\`（备份）、`%LOCALAPPDATA%\ZhixuERP\`（DeepSeek 密钥和三家机器人凭据 `bots\bots.sqlite`，用当前 Windows 账号加密，换电脑或换账号要重填）。

## Linux 服务器部署

### 安装

全新安装用 `yongle-carton-erp-v<版本>-linux-x64.tar.gz`（现在是 0.9.0）。不要复制 Windows 的 `runtime` 或 `node_modules`。先装中文字体（缺字体时启动会拒绝，单据排版靠它量字宽）：

```sh
sudo apt-get update
sudo apt-get install -y fonts-noto-cjk fontconfig
sudo fc-cache -f
fc-match 'Noto Serif CJK SC'
```

程序解压到 `/opt/yongle-carton-erp`（root 所有，服务账号只读）；数据、备份、凭据在 `/var/lib/yongle-carton-erp/` 下的 `data`、`backups`、`config`。

```sh
sudo sh /opt/yongle-carton-erp/scripts/linux/install-service.sh
sudo editor /etc/yongle-carton-erp/erp.env
sudo systemctl start yongle-carton-erp
sudo journalctl -u yongle-carton-erp -f
```

安装脚本建专用系统账号 `yongle-erp`，装 systemd 服务并开机自启（崩溃 5 秒后自动重启，日志进 journald），不自动首次启动、不覆盖已有配置、不改防火墙。停止、重启用 `systemctl stop|restart yongle-carton-erp`。

### 部署设置

写在 `/etc/yongle-carton-erp/erp.env`（示例 `scripts/linux/erp.env.example`）。**不要在这里写 API 密钥或机器人 Secret**，它们在网页的设置页填。

| 配置 | 用途和默认值 |
|---|---|
| `ERP_DEPLOYMENT` | `1` 启用部署；省略或 `0` 是本机模式 |
| `PORT` | 本机维护端口，默认 `3001` |
| `ERP_PROXY_PORT` | 给同机 Caddy 的回环端口，部署时默认 `3002`，不能和维护端口相同 |
| `ERP_ALLOWED_HOSTS` | 允许的域名，逗号分隔，部署时必填；非标准 HTTPS 端口要同时写进 Host 和 Origin |
| `ERP_ALLOWED_ORIGINS` | 允许的 HTTPS 写请求来源，默认由允许域名逐个加 `https://` |
| `ERP_BACKUP_COPY_DIR` | 每日完整备份另外复制到的绝对路径，默认关闭；要在 systemd 的 `ReadWritePaths` 里放行并给服务账号权限 |
| `ERP_BACKUP_COPY_KEEP` | 复制目录里自动备份保留几份，默认全留 |
| `DB_PATH`、`ERP_BACKUP_DIR`、`ERP_CONFIG_DIR` | 业务库、备份根目录、凭据目录。AI 工作区、原件、提示词、日志跟着业务库的目录 |

### HTTPS 和维护通道

- 两个端口都只监听本机回环：3001 给维护，3002 只给同机 Caddy。Caddy 配置照 `scripts/linux/Caddyfile.example`（代理会覆盖 `X-ERP-Client-IP`，不信访客伪造的头）；改完先 `caddy validate --config /etc/caddy/Caddyfile` 再重载。示例里限了请求体（21MB，程序里最大的上传是 20MB）和读请求的超时（不设写超时，助手是长时间边算边推）；改上传上限时两处一起改。服务器前还有别的代理时，先核对 Caddy 看到的对端地址是不是真实访客。
- 防火墙和云安全组只对员工开 80/443；3001、3002 不开；SSH 22 只放维护者 IP（改规则前先确认控制台网页登录能用作备用通道）。
- 维护和首次建管理员走 SSH 隧道，隧道不要监听 0.0.0.0，维护端口不能当公网代理的上游：

```sh
ssh -L 13001:127.0.0.1:3001 operator@your-server
```

  然后在本机打开 `http://127.0.0.1:13001`。维护电脑上同时开着本机 ERP 时，隧道改用 `http://localhost:13001`：Cookie 只按主机名区分，两边都用 `127.0.0.1` 会互相顶掉登录。
- 从域名进来的登录 Cookie 带 `__Host-` 前缀和 Secure（本机和维护通道照旧叫 `erp_session`），部署入口加 HSTS；从域名访问的健康检查只回 `ok`；部署时关掉服务器上的浏览器，员工网页里的页面控制照常。

### 从公网和从维护通道能做的事

- **只有维护通道能做**（从服务器本机回环地址登录的管理员才算“本机管理员”，从域名进来即使进了超级管理员模式也不算）：首次建管理员、初始化业务数据、数据管理（直接改档案、采购单、库存品、待核对的单据和生产任务；已生效的到货、送货、完工单只能编辑说明或更正，见[架构说明](架构说明.md)“单据流转和订单进度”）、AI 导入里改已导入的识别结果、复制成新文件和永久删除识别文件、助手的一键清空和数据管理命令。这些不可逆或绕过业务校验，有意不对公网开放。
- **从公网也能删：** 还没核对的单据有编辑权限就能删；已核对的单据和客户、产品、订单、供应商、采购单、库存品，要超级管理员账号先进超级管理员模式（账号菜单“系统维护”，输本人密码，15 分钟），确认时再输一次密码，服务器核验，删前自动快照、写审计。助手删除规则相同。代价是少了“只能本机删”这道门，账号密码要管好。
- **从公网改共用设置也要先进超级管理员模式：** 管理账号，改 AI 设置（密钥和识别设置）、提示词、机器人凭据、助手工具开关，都要先进模式；看、查余额、重新测试不用。
- **登录限频和排队：** 同一账号名从公网 15 分钟输错 20 次就锁（跨地址累计），维护通道照常能登，管理员被人锁住时从服务器登录；完整的限频规则见[架构说明](架构说明.md)“账号和权限”。核对密码同时只算 2 个，排不上的回“服务器正忙，请稍后再试。”（页面自动再试一次、不算输错）；从域名登录的人再多，维护通道登录和已登录的人验密码都排在前面。排队的几个常量（`server/core/hash-queue.ts`）是按开发机估的，部署后量一次登录耗时再调。

### 凭据和主密钥

- 凭据目录默认：Windows `%LOCALAPPDATA%\ZhixuERP`；Linux `$XDG_CONFIG_HOME/zhixu-erp`（没设就是 `~/.config/zhixu-erp`），部署时由 `ERP_CONFIG_DIR` 指定。
- Windows 用当前账号的 DPAPI 加密。Linux 用 AES-256-GCM，第一次自动生成 32 字节的 `credentials/master.key`；凭据根目录和密钥目录必须属于服务账号、权限 0700，密钥文件 0600、不能是链接。权限不对就拒绝启动，不会退回明文。不要用 `chmod 777` 解决权限错误。
- **主密钥不进任何备份，要单独加密保管。** 备份里有凭据库的密文，但没有主密钥解不开；丢了主密钥就到设置页重填。Windows 的凭据也不能跨平台解密，迁到 Linux 后 DeepSeek 密钥和机器人 Secret 要在服务器页面重填。

## 升级

### 补丁（小版本）

小版本只传变化的程序文件；大版本（如 0.9.0）和依赖有变化时用整包。**服务器上跑的必须是 GitHub 上某个已发布版本的代码**：本机、GitHub、服务器三方除了数据、配置、密钥和 `node_modules`，程序文件逐字节相同。

所以先发布（提交、打 `v版本号` 标签、推送、建 GitHub 发布，步骤在 Claude Code 的 `/release` 技能里，发布说明就是 `docs/CHANGELOG.md` 那一节），再在维护电脑的项目目录打补丁并核对三方一致（`--host` 是 SSH 配置里的主机名，默认 `yongle-erp`）：

```sh
npm run patch-server -- --dry-run
npm run patch-server
npm run patch-server -- --check
```

- `--dry-run` 只列差异。正式打之前先检查：本机没有未提交的改动、当前提交打了 `v版本号` 标签、GitHub 上同名标签指向同一个提交，不满足就拒绝并说明。
- `--check` 列出三方的版本和提交并逐个比对文件，一致退出码 0，不一致列原因、退出码 1。
- `--hotfix "原因"` 只用于服务器紧急故障：跳过发布检查直接打，服务器记为“临时修复，未发布”，事后必须补发正式版本。
- 出问题回滚：检出上一个版本标签再打一次补丁，或用服务器上的回滚副本。
- `--base 服务器上解压好的旧版安装目录 --out 本机输出目录` 只生成发布补丁、不上传：输出补丁文件和执行补丁的三个脚本 `apply-patch.mjs`、`patch-logic.mjs`、`patch-rollback.mjs`（各带 `.sha256`；清单是 `scripts/patch-server.mjs` 的 `applyScripts`），三个脚本要放在同一个目录运行。

补丁做了什么：只取 git 跟踪的程序文件（清单在 `scripts/release-files.mjs`，整包共用），有没纳入 git 的、被忽略的、符号链接、通不过发布扫描的（数据库、密钥、证书）就拒绝；本机类型检查并把页面构建到临时目录；和服务器逐个比对 sha256（Windows 换行转成 LF，`.cmd` 保持 CRLF）；上传变化的文件和执行补丁的三个脚本（`scripts/linux/` 下的 `apply-patch.mjs`、`patch-logic.mjs`、`patch-rollback.mjs`）。`erp.env` 里的 `ERP_CONFIG_DIR` 不是绝对路径时直接拒绝、不打（程序本身这时也起不来，先改 `erp.env`）。服务器上先记下补丁开始时间和业务库结构版本、做一次完整备份、存回滚副本，再停服务、换文件、启动、查健康和版本；读不出版本或备份失败就什么都不改。`package-lock.json` 有变化时拒绝（补丁不能重装原生依赖）。补丁只改 `/opt/yongle-carton-erp`，配置不碰。

启动失败或 90 秒内健康检查不过就自动回滚：停服务、换回旧文件，**先换回配置库，再看业务库**。

新程序启动时可能已经升级了配置库（账号、提示词、AI 设置等，见[数据模型](数据模型.md)“其他数据库”），旧程序会因为它们“比程序新”起不来，所以先换回：

- 换回来的旧程序有 `revert-config-upgrades` 命令（看换回来的 `erp.sh` 里有没有这个动作）：以服务账号运行它，把补丁开始以后升级过的配置库换回升级前备份。命令报失败（拒绝的几种情况见“备份和恢复”的“换回配置库”）就转人工。
- 旧程序没有这条命令（0.9.0 的程序）：在数据目录、配置目录下各 `snapshots/` 里找补丁开始以后做的配置库升级前备份，每个库取最新一份，以服务账号只读看库现在的版本，只算真正升级过的库（版本等于备份写的“到第几版”）。一个都没有就不用换回，接着往下；有就转人工，提示里列出这几个库和备份；读不出某个库的版本也转人工，提示写明是哪个库。
- 转人工：服务保持停止，按打印的步骤逐个换回：把现在的库连同旁边的 `-wal`、`-shm`、`-journal` 改名留在 `snapshots/` 下（`<库文件名>-before-revert-manual-时间`，不要删），再把升级前备份复制回去。命令跑过但失败的，已经换回的库看上面的输出，步骤只列还没换回的；接着又读不出库的版本时，列出补丁开始以后的全部配置库升级前备份（每个库最新一份），要逐个确认库现在的版本，是备份写的“到第几版”的才换。步骤里写明业务库变了没有：没变就换完配置库直接启动，变了或判断不了就接着照步骤用补丁前的完整备份恢复。

配置库换回以后，新程序运行期间改的配置（新账号、改过的长期记忆和提示词、AI 设置、机器人设置）不在换回的库里，在换下来的 `-before-revert-` 文件里，需要时人工补录；账号库换回后没有登录会话，**所有人要重新登录**。这些文件见“备份和恢复”。

再看业务库：

- 结构版本没变：直接启动旧程序。
- 新版本已经升级了数据库：用补丁前的完整备份恢复数据库再启动旧程序。备份以后的写入不在恢复后的库里，原数据目录另存为 `data.before-restore-时间`，需要时人工补录；所有人要重新登录。
- 判断不了（读不出版本、找不到备份、停服务失败）：服务保持停止，按打印的步骤手动恢复，不要直接启动旧程序。

同一时间只允许一个补丁在跑（锁 `/run/yongle-carton-erp-patch.lock`）。补丁不怕 SSH 断开，全过程记在 `/var/backups/yongle-carton-erp-patches/补丁编号/apply.log`，回滚副本 `rollback.json`（含补丁开始时间）也在那里。断线后重新连上查结果：

```sh
ssh yongle-erp sudo tail -n 40 /var/backups/yongle-carton-erp-patches/补丁编号/apply.log
npm run patch-server -- --check
```

日志最后是“补丁已应用”就成功了；写着“回滚”或“补丁未应用”就是没打上，按日志说明处理。每次补丁记在程序目录的 `.release-package`（`commit` 当前提交、`released` 是否正式发布、`patches` 历次补丁）。

### 整包

1. 备份（`npm.cmd run backup` 或 `erp.sh backup`），停止服务。
2. 新版本解压到新目录（Windows 把旧目录的 `data\`、`backups\` 复制过去；Linux 替换 `/opt/yongle-carton-erp`，数据目录不动）。
3. 启动。新版本改了数据库结构时，启动先拍升级前快照，再在一个事务里按编号逐步升级，失败整体退回、数据不动，启动窗口写明原因。配置库也一样，升级前备份在各库文件旁边的 `snapshots/`。
4. 要退回旧版本：停服务，换回旧程序，先换回配置库（Linux `erp.sh revert-config-upgrades`；Windows 在旧目录的维护命令行里手动运行 `npm.cmd run revert-config-upgrades`：旧目录的 `data\` 没动过，但 AI 设置、机器人设置在新旧共用的 `%LOCALAPPDATA%\ZhixuERP\`，不换回旧程序打不开），再看业务库：结构版本变了就用第 1 步的备份恢复。旧程序没有这条命令时照上面“转人工”的做法手动换回。换回以后的影响同补丁回滚。

### 0.9.0 以前的旧数据

0.9.0（已发布）起业务库从空库开始，建表定为第 20 版：**0.9.0 以前的业务库和备份都不能升级或恢复；从 0.8.x 升上来只能用整包，不能打补丁**（打了会因旧库启动失败、自动换回旧文件）。

- **碰到旧业务库：** 程序拒绝启动（提示“这是 0.9.0 以前的旧业务数据库”），旧库不动，提示里写明要移走哪几样。先用 0.8.4 做一次完整备份另存到别的磁盘（以后只有 0.8.4 能恢复它），再在业务库所在目录（本机是安装目录的 `data/`，服务器是 `/var/lib/yongle-carton-erp/data/`）把这三样**移走保存、不要删**：`erp.sqlite`（连同 `erp.sqlite-wal`、`erp.sqlite-shm`）、`import-archive/`、`ai-imports/`（识别工作区按编号引用客户产品，接不上新库）。再启动，程序建空库；之后按首次使用建管理员和各个账号，在“设置 → API 配置”重填 DeepSeek 密钥，在“设置 → 消息接入”重填机器人的应用编号和 Secret。
- **旧配置库：** 账号、AI 设置、提示词、助手工具设置这几个库，打开时认出是 0.8.4 的就整个删掉、按新结构重建（`server/core/versioned-sqlite.ts`）；机器人设置在配置目录 `bots/bots.sqlite`，旧位置的不再读。提示词、助手工具开关、单据模板、财务科目和凭证模板都是默认值。
- **可以删的旧文件：** 配置目录下的 `wecom/`；数据目录 `ai-prompts/` 里的 `shipping-marks.sqlite`、`purchase-orders.sqlite`、`customer-deliveries.sqlite`。
- **退回 0.8.4：** 停掉 0.9.0 以后的程序，换回 0.8.4，用 0.8.4 做的完整备份恢复（配置库已被重建，只把移走的三样放回去不够）。0.9.0 以后录的数据带不回去。

## 客户端更新包

安卓 App 和 Windows 电脑客户端（`apps/`）的“检查更新”先读服务器上的版本清单，再下载安装包。清单和安装包放在同一个域名下的固定目录，由 Caddy 直接当静态文件发，不经 ERP 程序、不用登录：

| 地址 | 是什么 |
|---|---|
| `https://erp.nbyongle.cn/app-update/android/manifest.json` | 安卓版本清单（格式见 `apps/android/docs/构建与测试.md`“应用内更新”） |
| `https://erp.nbyongle.cn/app-update/android/<安装包>.apk` | 安卓安装包 |
| `https://erp.nbyongle.cn/app-update/windows/latest.json` | Windows 版本清单（Tauri 的格式，见 `apps/desktop/docs/构建与测试.md`“应用内更新”） |
| `https://erp.nbyongle.cn/app-update/windows/<安装包>.exe` | Windows 安装包 |

- **服务器目录：** `/srv/yongle-erp-app-update/android/`、`/srv/yongle-erp-app-update/windows/`，属于维护账号、Caddy 能读（目录 0755、文件 0644）。不放进 ERP 的安装目录和数据目录，升级 ERP、备份恢复都不碰它。安装包文件名只用字母、数字、`.`、`-`、`_`（Windows 打包出来的中文名上传时改掉，清单里写改后的名字）。
- **Caddy：** 写法只在 `scripts/linux/Caddyfile.example` 里 `/app-update/` 那一段：这个前缀下的请求由 Caddy 从上面的目录直接发文件，找不到（目录还没建也一样）回 404，不会交给 ERP；清单不让缓存。服务器上的 Caddy 配置已照它补上这一段，以后改完先 `caddy validate --config /etc/caddy/Caddyfile` 再重载。
- **发新版的顺序：** **先**把安装包传到对应目录，确认能从域名下载、sha256 一致，**再**传清单。顺序反了，客户端会看到新版本却下不到包。打包、签名、清单怎么写见 `apps/android/docs/构建与测试.md`、`apps/desktop/docs/构建与测试.md` 的“正式发布的顺序”。
- **客户端里的地址：** 只在打包时写进安装包（安卓 `releaseUpdateUrl`，Windows `config/app.json` 的 `updateUrl`、`updatePubkey`），现在都留空；第一个正式版发出去之前必须填好，否则装出去的客户端永远不会自己更新（见[路线图](路线图.md)“应用外壳发第一个正式版和真机测试”）。正式版打开的 ERP 地址（安卓 `apps/android/app/build.gradle.kts` 的 `releaseUrl`、Windows 的 `erpUrl`）已经是服务器域名。

## 备份和恢复

| 类型 | 说明 |
|---|---|
| 手动完整备份 | `npm.cmd run backup`，生成 `backups/full-时间/`，运行中可以做。唯一的手动备份命令 |
| 自动备份 | 服务运行时每天一次，`backups/auto-时间/`，保留最近 14 份；失败时今日页提示 |
| 删除前快照 | 删除、初始化、本机管理员直接改订单前自动拍，`data/snapshots/`；拍不成就停止该操作。最近 24 小时的全留，更早的留 20 份。只含业务库，不含原件 |
| 升级前快照 | 启动时发现业务库要升级才拍，`data/snapshots/upgrade-v旧版-to-v新版-时间.sqlite`，留最近 3 份 |
| 配置库升级前备份 | 启动时发现配置库要升级才做，在库文件旁边的 `snapshots/` 下（如 `data/security/snapshots/`、配置目录的 `ai/snapshots/`），叫 `<库文件名>-upgrade-v旧版-to-v新版-时间.sqlite`。同一个“从第几版到第几版”只留最新一份，最多留最近 3 个版本对，自动清理。账号库的不带登录会话。补丁回滚换回配置库时用它；确认不会再退回升级前的程序后也可以手动删 |
| 换下来的配置库 | 换回配置库时，换下来的那份留在同一个 `snapshots/` 下，叫 `<库文件名>-before-revert-时间.sqlite`（手动换回的叫 `-before-revert-manual-时间`，旁边可能带 `-wal` 等）。里面是新程序运行期间的配置，账号库的已去掉会话。不自动清理：核对完、要补录的补完就可以删 |
| 升级没做完留下的备份 | 某一步升级自己结束了事务（程序问题）、库成了半截时，这次的升级前备份改名留在 `snapshots/` 下，叫 `<库文件名>-before-unfinished-v旧版-to-v新版-时间.sqlite`。不自动清理；**有它这个库以后打开都会拒绝**。处理：先停掉程序，把它移到库文件的位置、覆盖半截的库（库旁边有 `-journal` 这类附属文件一起删掉），移走以后就不再挡着，换上修好的程序（或旧版本的程序）启动 |

Linux：

```sh
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh backup
sudo systemctl stop yongle-carton-erp
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh restore /absolute/backup-directory
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh reset-password 用户名
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh revert-config-upgrades [补丁开始时间]
```

- **换回配置库：** `revert-config-upgrades`（Windows `npm.cmd run revert-config-upgrades -- [时间]`）要先停服务。把比当前程序新的配置库换回从当前版本升上去时做的升级前备份；给了时间（如 `2026-11-21T10:00:00.000Z`）只用这个时间以后做的。逐个打印换回了哪个库、换进去的备份、换下来的文件在哪，换回了账号库会提示所有人要重新登录；没有要换的打印“没有比当前程序新的配置库，不用换回。”。有换不回的逐个打印原因、退出码 1，那个库不动；补丁回滚时就转人工。补丁回滚和整包退回时用（见“升级”）。会拒绝换回的情况：
  - 找不到从当前版本升上去的升级前备份（给了时间的，只看这个时间以后做的）：确认程序版本对不对，或到库旁边的 `snapshots/` 找合适的备份手动换。
  - 库文件旁边还有 `-wal`、`-shm`、`-journal`：上次没有正常关掉（比如新程序被杀），里面可能有没写完的改动，不能直接换。先确认服务已经停止，再照“升级”里转人工的做法：把库连同这几个文件一起改名留在 `snapshots/` 下（不要删），再把升级前备份复制回去；拿不准就交给维护人员。
  - 默认位置算不出来（提示“默认位置算不出来”，多半是 `ERP_CONFIG_DIR` 不是绝对路径）：看不了那个库要不要换。把 `erp.env` 的 `ERP_CONFIG_DIR` 改成和服务同一个绝对路径，用和服务同一套设置再运行一次。

- **备份里有：** 业务库、账号、AI 工作区和原件、归档、提示词、助手工具设置、出错记录，以及加密的 AI 配置和机器人配置（在 `_extra/`，机器人的叫 `bots.sqlite`）。清单 `manifest.json` 记程序版本、业务库结构版本和每个配置库的版本。
- **不要直接复制 `erp.sqlite` 当备份：** 运行中的库是 WAL 模式，复制出来可能缺最近的写入，恢复时会被拒绝。
- **恢复：** 先停服务，再 `npm.cmd run restore -- "备份目录绝对路径"`；要用和服务同一套 `DB_PATH`、`ERP_CONFIG_DIR` 运行。恢复前的 `data/` 另存为 `data.before-restore-时间`，中途失败自动退回。`restore` 也收单个业务库文件（备份里的 `erp.sqlite` 或 `data/snapshots/` 下的快照），只恢复业务库。
- **恢复前先全部校验：** 清单、sha256、每个数据库文件都过了才动现有数据，有一个不过整份拒绝。拒绝的有：WAL 模式的副本（旧格式备份、直接复制的库）、0.9.0 以前的业务库和配置库、比当前程序新的、版本记录不完整的、不是本系统的、结构被改过的。配置库比程序旧但在 0.9.0 以后的照常恢复，启动时升级、数据留着。`_extra/` 里的 AI 配置和机器人配置不覆盖本机，不论版本只查完整性；认不出是哪个配置库的文件也只查完整性，恢复完命令会列出这些“只查了完整性的文件”。
- 业务库比程序新（比如补丁回滚后）时照样能备份，清单标 `newerSchema`，只能用支持该版本的程序恢复。
- **离机保存：** 同一块硬盘坏了备份也没了。定期把备份复制到别的磁盘；服务器上的另一个目录不算离机，要挂载或传出服务器。定期做一次隔离的恢复演练。

## 日常维护和排查

### 每日清理

服务启动 5 分钟后跑第一次，之后每小时看一次，满 24 小时才再清；数据库正忙就等下个小时。清掉东西时日志写一行“每日清理：……”。

- 防重复提交记录保留 90 天。
- 订货单、送货单导出的文件内容保留 180 天，之后只删文件，记录、单号、交付状态都留着。
- 收件箱里待处理、已忽略的消息收到 180 天后连附件一起删，已处理的（包括转成单据的）留着。
- 把删数据空出来的空间还给磁盘（库大时这一下稍慢）。
- 连续运行满 24 小时和关闭时更新一次查询统计。

### 排查问题

- **问助手：** 员工说点了没反应、保存不了，可以让助手查：最近出错和被拒的请求（服务端记的和页面上报的，保留 30 天；普通账号只看自己的，超级管理员看全部）、按人按时间的修改记录、后台任务。超级管理员还能让它看运行日志（按字、按时间找）、登录记录和程序代码（只读）。
- **日志在哪：** 业务库目录下的 `logs/`：`run.log` 是运行日志（满 2MB 轮换成 `run.log.1`），`problems.sqlite` 是出错记录。Linux 还可以 `journalctl -u yongle-carton-erp`。
- **“数据没有保存：有内容不符合数据规则，请联系维护人员。”**：数据库规则（状态取值、真实日期、单位只收“只”“张”、金额不为负等）挡住了写入，什么都没存。这说明程序本该先拦下却没拦，是程序问题。日志里有一行以 `[数据规则]` 开头，写明入口和被哪条规则挡住（不带写入的值），交给开发的人。
- **启动被拒绝（数据都不动）：**

| 启动窗口的提示 | 原因和做法 |
|---|---|
| 这是 0.9.0 以前的旧业务数据库 | 按“0.9.0 以前的旧数据”移走旧库 |
| 数据库比当前程序新 | 多半是补丁回滚只换回了程序。换回新程序，或用补丁前的完整备份恢复 |
| 这个文件不是本系统的业务数据库 | `DB_PATH` 指错了 |
| 业务数据库的版本记录不完整 | 库被改坏了，用最近的完整备份恢复 |
| 业务数据库的表结构和当前程序对不上 | 版本记录是当前版，表结构却和程序新建的不一样（开发阶段直接改了建表、或被数据库工具改过），提示里列出差在哪几张表。正式数据用最近的完整备份恢复；开发用的库移到别的地方保存，再启动建新库。升级走完以后结构对不上也一样，整次升级退回，库不变 |
| 某个配置库比当前程序新 | 多半是回滚只换回了程序。停服务后运行 `revert-config-upgrades` 换回配置库（见“备份和恢复”），或换回新程序 |
| 某个配置库从第 a 版升级到第 b 版失败，已整体退回 | 文件没有改动。换回旧版本的程序继续用，把提示交给维护人员 |
| 某个配置库升级停在某一步：这一步自己结束了事务，升级没有做完 | 程序问题，这是唯一文件可能已经改动的情况：库是半截的，升级前备份已改名成 `-before-unfinished-`，以后打开都会拒绝（提示“上次升级没有做完，库是半截的”）。按提示的“处理办法”做，见“备份和恢复”里“升级没做完留下的备份”；把提示交给维护人员 |
| 某个配置库要从第 a 版升级到第 b 版，升级前备份没有做成 | 没有开始升级、文件没动。检查提示里那个目录的磁盘空间和读写权限后再启动 |
| 某个配置库比基线（第 N 版）旧，要删掉重建，但文件删不掉 | 关掉占用它的程序后再启动 |

- **`revert-config-upgrades` 没换回：** 提示里写明是哪个库、什么原因（找不到升级前备份、库旁边还有 `-wal` 等附属文件、默认位置算不出来），各自怎么办见“备份和恢复”的“换回配置库”。

### 账号

- 第一次使用在登录页建管理员（服务器上要走维护通道）。
- 员工忘记密码在登录页提交，管理员在“账号管理”确认后发临时密码。
- 管理员忘记密码：在服务器本机运行 `npm.cmd run reset-password -- "用户名"`（Linux 用 `erp.sh reset-password 用户名`），生成 24 小时内有效的临时密码，旧登录立即失效，登录后必须先改。

### 消息机器人

企业微信、飞书、钉钉三家都用长连接，不用公网地址，只要服务器能出站访问 `openws.work.weixin.qq.com`、`open.feishu.cn`（和它给的长连接地址）、`api.dingtalk.com`（和它给的 Stream 地址，回复发到 `*.dingtalk.com`）。三家可以同时开，在“设置 → 消息接入”各一张卡片，填好点“保存并连接”，状态显示“已连接”才收得到。

- **企业微信：** ① 管理后台创建智能机器人，API 模式选“使用长连接”；② 复制 Bot ID，点获取 Secret；③ 设好哪些人能用；④ ERP 企业微信卡片填好，点“保存并连接”；⑤ 单聊发文字、图片、文件试一下。
- **飞书：** ① 开发者后台创建“企业自建应用”；② 添加应用能力“机器人”；③ 权限管理开通“读取用户发给机器人的单聊消息”（`im:message.p2p_msg:readonly`）、“接收群聊中 @ 机器人消息事件”（`im:message.group_at_msg:readonly`）、“获取与发送单聊、群组消息”（`im:message`，下载文件和回复要它）；④ “凭证与基础信息”复制 App ID、App Secret；⑤ 先在 ERP 飞书卡片填好、点“保存并连接”（飞书要求长连接在线才能保存下一步）；⑥ “事件与回调”订阅方式选“使用长连接接收事件”，保存；⑦ 添加事件“接收消息”（`im.message.receive_v1`）；⑧ 创建版本、设可用范围、发布；⑨ 单聊机器人发文件试一下。
- **钉钉：** ① 开发者后台创建“企业内部应用”；② “凭证与基础信息”复制 Client ID、Client Secret；③ 添加应用能力“机器人”，消息接收模式选“Stream 模式”，发布机器人；④ 权限管理开通“企业内机器人发送消息权限”（`qyapi_robot_sendmsg`，下载文件要它）；⑤ 设可见范围并发布；⑥ ERP 钉钉卡片填好、点“保存并连接”；⑦ 单聊机器人发文件试一下。
- **同一个应用只连一处：** 企业微信后连上的会顶掉先连的、不会自动抢回；飞书、钉钉会把消息随机发给其中一处，更不容易发现。测试实例别和正式实例连同一个应用，切换时先断开旧的再连新的。
- **卡片上的状态：** “已连接”才收得到；“连接中”“连接断开，正在重试”是网络断了、对方限流或临时出错，程序自己按退避重试，红字写着“××暂时连不上（错误码 N），正在重试”，等着就行，一直不好再查服务器出站网络；“连接被拒绝”是凭据或后台配置不对，不会再重试，红字写着原因（如“钉钉拒绝连接（错误码 401）：请检查 Client ID 和 Client Secret。”），改对后点“保存并重新连接”；换了服务器、平台或服务账号后红字是“已保存的 Secret 在这台机器上解不开……请重新填写 Secret。”，重填一次；“已被其他连接顶替”只有企业微信有，说明同一个机器人在别处连上了。
- 系统关着时收不到消息，官方没说之后会不会补发。

## 打包和 Linux 验证

两个包用同一个脚本，必须在各自平台的 Node 24 x64 上打（`--target win-x64` 或 `linux-x64`），不能复制别的平台的原生依赖；主密钥不进安装包。程序文件清单在 `scripts/release-files.mjs`，新加运行时要用的脚本或目录要加进去；发布扫描规则在 `scripts/release-scan.mjs`，整包和补丁共用。

Linux 验证在独立的 Ubuntu 24.04 WSL 原生目录里用虚构数据做，不在 `/mnt/c` 下装依赖，不碰 Windows 的数据、备份和凭据目录；源码按白名单复制，依赖在 Linux 上重新装：


## 项目里不能随手删的

- 数据目录、备份目录、用户配置目录受保护：整理项目时不清库、不初始化、不删原件、归档、审计和凭据。
- `node_modules`、`dist`、`.build-tmp-*`、`.playwright-cli` 和测试日志可以由安装、构建、测试重新生成。
- 本机的 `work/`、`output/`、`outputs/` 混有验收样张、截图、旧克隆和安装包，不能只凭目录名删，先查 Git 状态、引用和来源。
