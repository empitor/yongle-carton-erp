# 部署与运维

Linux 主线为 Ubuntu 24.04 LTS x64，Windows 本机和 Windows Server 作为备选保留。同一套代码提供两个原生安装包，同机 Caddy 负责 HTTPS。

## Linux 部署（Ubuntu 24.04 LTS x64）

### 软件与账号

全新安装用 Linux 包 `yongle-carton-erp-v0.8.2-linux-x64.tar.gz`，装好后按最新版本的发布说明打补丁升级（目前是 0.8.4，一个补丁从 0.8.2 直接升到 0.8.4）。包内置 Node.js 24（24.15 或更高的 24.x）、Linux 原生依赖和已构建页面。不要复制 Windows 的 runtime 或 node_modules。安装中文字体：

```sh
sudo apt-get update
sudo apt-get install -y fonts-noto-cjk fontconfig
sudo fc-cache -f
fc-match 'Noto Serif CJK SC'
```

字体包见 [Ubuntu 官方说明](https://packages.ubuntu.com/noble/fonts-noto-cjk)。缺字体时启动明确拒绝；每张默认行数仍须为 6/11/11/24/14。语音模型可选，缺少模型只影响语音，不影响其他模块。

语音模型放在 `/opt/yongle-carton-erp/vendor/models/sensevoice/`，只需 `model.int8.onnx` 和 `tokens.txt`，来源见包内 `vendor/models/README.md`。国内服务器连不上 Hugging Face 时可从 hf-mirror.com 同路径下载，下载后核对 sha256：`model.int8.onnx` 为 `c71f0ce0…2cd51`，`tokens.txt` 为 `f449eb28…1a1dc`。模型首次使用语音时加载，放入后不用重启。2 核 4G 实测加载约 1 秒、常驻约 400MB，5.6 秒中文语音识别约 0.4 秒。安装包不含模型，升级替换程序目录前先把这两个文件拷出来，装好新版本后放回原处。

程序解压至 `/opt/yongle-carton-erp`，root 所有，服务账号只读。数据、备份、凭据分别位于 `/var/lib/yongle-carton-erp/data`、`backups`、`config`。AI 工作区、原件、提示词与工具设置跟随 `DB_PATH` 的目录，程序目录无需可写。

```sh
sudo sh /opt/yongle-carton-erp/scripts/linux/install-service.sh
sudo editor /etc/yongle-carton-erp/erp.env
sudo systemctl start yongle-carton-erp
sudo journalctl -u yongle-carton-erp -f
```

安装脚本创建专用 `yongle-erp` 系统账号，安装 systemd 服务并启用开机自启，但不自动首次启动、不覆盖已有配置、不改防火墙。崩溃自动重启，日志进入 journald。配置须改成实际域名，禁止填写 API 密钥或机器人 Secret。停止/重启使用 `systemctl stop/restart yongle-carton-erp`。

### HTTPS 与维护通道

两个 ERP 端口均只监听回环：3001 用于本机维护，3002 专供同机 Caddy。使用 `scripts/linux/Caddyfile.example`，代理覆盖 `X-ERP-Client-IP`，不信任访客伪造的请求头。参见 [Caddy 官方反向代理说明](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。先执行 `caddy validate --config /etc/caddy/Caddyfile`，再按管理流程重载。

防火墙和云安全组仅向员工开放 80/443；3001/3002 不对外开放，SSH 22 仅允许维护者指定 IP。先确认备用管理通道再改规则。维护和首次建立管理员通过 SSH 隧道：

```sh
ssh -L 13001:127.0.0.1:3001 operator@your-server
```

维护人本机访问 `http://127.0.0.1:13001`，隧道不要监听 0.0.0.0。0.8.2 及更早版本只认 3001 和 5173 两个来源，隧道本机端口要用 `5173`（`ssh -L 5173:127.0.0.1:3001 …`），否则提交时提示“请求来源不允许”。维护电脑上同时开着本机 ERP（`127.0.0.1:3001`）时，隧道改用 `http://localhost:端口` 打开：浏览器的 Cookie 只按主机名区分、不分端口，两边都用 `127.0.0.1` 会互相顶掉登录。严禁把维护端口用作公网代理上游。

### 凭据、备份与迁移

`ERP_CONFIG_DIR` 可指定绝对凭据目录。Windows 默认仍为 `%LOCALAPPDATA%\ZhixuERP`；Linux 默认 `$XDG_CONFIG_HOME/zhixu-erp`，未设置 XDG 则为 `~/.config/zhixu-erp`。`DB_PATH` 指定业务库，`ERP_BACKUP_DIR` 指定本地备份根目录。

Windows 保留 CurrentUser DPAPI，旧无标记密文兼容读取，新写密文带 `dpapi:v1:`。Linux 使用 AES-256-GCM（`aes256gcm:v1:`），首次自动生成随机 32 字节 `credentials/master.key`；凭据根目录和密钥目录须属服务账号且为 0700，密钥为该账号所有的 0600 常规文件，无链接。权限错误拒绝启动，绝不降级明文，不在日志、报错或审计输出主密钥。

**主密钥不进入任何业务备份，请单独加密保管。** 完整备份保留凭据数据库的密文副本，但单靠业务备份不能解密 Linux 凭据；主密钥遗失后需重新填写。不要通过 chmod 777 解决权限错误。

Windows 迁 Linux：先完整备份并离机保管，维护窗口停止旧实例，在服务器以同一服务账号恢复，核对业务和附件，再启动。Windows DPAPI 凭据不能跨平台解密，AI 密钥和机器人 Secret 在新服务器页面重新填写。机器人先停旧连接再启新连接。

```sh
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh backup
sudo systemctl stop yongle-carton-erp
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh restore /absolute/backup-directory
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh reset-password 用户名
```

每日备份及 `ERP_BACKUP_COPY_DIR/ERP_BACKUP_COPY_KEEP` 保持有效。离机位置须挂载或另行传出服务器，本机另一目录本身不算离机。使用外部复制位置时，通过 systemd override 将其加入 `ReadWritePaths` 并授予服务账号权限。定期做隔离恢复演练，主密钥始终单独保管。

### 小版本补丁升级

小版本只传有变化的程序文件，不传整包；大版本（如 0.9.0）和依赖变化时仍用整包。

**原则：服务器上跑的代码必须是 GitHub 上某个已发布版本的代码。** 本机、GitHub、服务器三方除了业务数据、配置、密钥、`node_modules` 和语音模型以外，程序文件逐字节相同。修 bug 的流程：

1. 本机修改并补测试，类型检查和全量测试通过。
2. 改版本号（修 bug 加最后一位，加功能加中间一位），更新 CHANGELOG 和发布说明。
3. 提交，打 `v版本号` 附注标签，推送：`git push origin main v版本号`。
4. 打补丁上服务器，再用 `--check` 核对三方一致。
5. 出问题时回滚：检出上一个版本标签，再打一次补丁；或用服务器上的回滚副本。

在维护电脑的项目目录运行，`--host` 是 SSH 配置里的主机名，默认 `yongle-erp`：

```sh
npm run patch-server -- --dry-run
npm run patch-server
npm run patch-server -- --check
```

- `--dry-run` 只列出差异，不上传。
- 正式打补丁前先做发布检查：本机没有未提交的改动、当前提交打了 `v版本号` 标签、GitHub 上的同名标签指向同一个提交。任何一条不满足就拒绝，并说明怎么处理。
- `--check` 列出本机、GitHub、服务器三方的版本和提交，逐个比对程序文件，一致时退出码 0，不一致时列出原因、退出码 1。
- `--hotfix "原因"` 只用于服务器紧急故障：跳过发布检查直接打上去，服务器记录为“临时修复，未发布”。事后必须按上面的流程补发正式版本，`--check` 才会恢复一致。

正式运行的步骤：
1. 本机类型检查，把页面构建到临时目录。
2. 和服务器的程序文件逐个比对 sha256。本机的 Windows 换行会先转成和服务器一致的 LF，`.cmd` 保持 CRLF。
3. 打包上传有变化的文件。
4. 在服务器上执行：完整备份业务数据、保存回滚副本、停服务、替换文件、启动并检查健康和版本。启动失败或 90 秒内健康检查不通过，就自动换回旧文件再启动。
5. 再比对一次，确认服务器和本机完全一致。

`package-lock.json` 或依赖有变化时脚本会拒绝打补丁，因为补丁不能重装原生依赖。程序文件清单在 `scripts/release-files.mjs`，整包和补丁共用。补丁只改 `/opt/yongle-carton-erp`，不碰数据目录、配置和语音模型。每次补丁记在程序目录的 `.release-package` 里：`commit` 是当前程序对应的提交，`released` 表示是否正式发布，`patches` 是历次补丁。回滚副本放在 `/var/backups/yongle-carton-erp-patches/补丁编号/`。

### Linux 验证与打包

开发验收使用独立 Ubuntu 24.04 WSL 原生目录和虚构数据，不在 `/mnt/c` 下安装依赖，不访问 Windows 的 data、backups、凭据目录。源码经白名单复制，依赖在 Linux 重新安装。

```sh
export LOCALAPPDATA="$(mktemp -d)"
export ERP_CONFIG_DIR="$LOCALAPPDATA/config"
export DB_PATH="$LOCALAPPDATA/unused.sqlite"
npm ci
npx tsc --noEmit
npm test
node --import tsx scripts/linux/verify-runtime.mjs
npm run package -- --target linux-x64 --out "$LOCALAPPDATA/packages"
```

Windows 使用同一打包脚本的 `--target win-x64`。两个目标必须在各自原生平台运行；两包分别检查清单、sha256、干净目录启动、虚构账号登录和单据导出。systemd、Caddy 和实际公网 TLS 仍需服务器上线时验收。

## 日常运维（本机）

### 启动和停止

- 启动：双击 `启动系统.cmd`。发布包直接启动；源码目录会先构建，再启动服务并打开浏览器，窗口要保持打开。
- 停止：双击 `停止系统.cmd`，或在原窗口按 `Ctrl+C`。
- 地址：`http://127.0.0.1:3001`。端口用环境变量 `PORT` 改。
- 环境：Node.js 24.15 或更高的 24.x。

同一个数据库只能有一个实例，由 `data/erp.sqlite.running` 锁定。进程异常退出留下的锁，下次启动会自动清理。

### 更新版本

1. 备份：`npm.cmd run backup`
2. 停止服务
3. 取新代码（如需要）并安装依赖：`npm.cmd ci`
4. 启动。数据库迁移会自动执行；订单状态规则有变化的版本，第一次启动时还会按新规则重算一次订单状态，启动窗口会显示改了几张。

### 备份和恢复

| 类型 | 说明 |
|---|---|
| 手动完整备份 | `npm.cmd run backup`，生成 `backups/full-时间/`，运行中可执行 |
| 自动备份 | 服务运行时每天一次，`backups/auto-时间/`，保留最近 14 份 |
| 删除前快照 | 物理删除和初始化前自动保存，`data/snapshots/`，保留最近 20 份；只含业务库，不含原件归档（初始化清业务记录时原件归档一并删除） |
| 升级前快照 | 启动检测到待执行迁移时保存到 `data/snapshots/upgrade-*.sqlite`。只含业务库，单独留存，生成失败时启动中止 |

- 备份包含业务库、账号、AI 工作区和原件、归档、提示词、AI 配置和机器人配置（后两者是加密内容）。
- **恢复：** 先停止服务，再执行 `npm.cmd run restore -- "备份目录绝对路径"`。恢复前的 `data/` 另存为 `data.before-restore-时间`；中途失败会自动退回原数据，退回也失败时报错里写明副本位置。迁移版本缺号的备份拒绝恢复。本机 AI 配置不会自动覆盖。
- **请定期把备份复制到其他磁盘。** 同一块硬盘坏了，备份也一起没了。
- 自动备份失败时今日页会提示。

### 账号

- 首次使用在登录页创建管理员。
- 员工忘记密码：在登录页提交，管理员在“账号管理”确认后生成临时密码。
- 管理员忘记密码：在服务器本机运行 `npm.cmd run reset-password -- "用户名"`，生成临时密码，24 小时内有效，旧登录立即失效，登录后必须先改。

### 企业微信机器人

- 在 设置 → 消息接入 填 Bot ID 和 Secret。后台要把 API 模式设为“长连接”，不需要公网地址。
- 同一个机器人只能连一处。测试实例和正式实例不要同时连，后连上的会把先连的顶掉，且不会自动抢回。
- 软件关着时收不到消息。官方没有说明之后是否补发，所以部署前电脑要常开。

## Windows Server 部署

```text
员工浏览器 → HTTPS 反向代理（Caddy 或 IIS）→ 127.0.0.1:3002
维护人 → 远程桌面 → 服务器本机浏览器 → 127.0.0.1:3001
```

### 安装和配置

1. 在 Windows Server 安装 Node.js 24.15 或更新的 24.x，使用 `node --version` 验证。准备专用普通 Windows 账号，授予“作为批处理作业登录”，登录一次建立其用户配置目录。管理员通过受限远程桌面维护系统。
2. 把已审阅的代码版本取到服务器的独立发布目录。给服务账号授予程序目录的读取、执行权限，并对发布目录下的 `data`、`backups` 和外置日志目录授予写入权限。在发布目录执行 `npm.cmd ci`。将构建输出先放到新目录，成功后将该产物放入尚未运行的新发布目录的 `dist`。

   ```powershell
   npx.cmd tsc --noEmit
   $stage = Join-Path ([IO.Path]::GetTempPath()) ('erp-dist-' + [guid]::NewGuid())
   npx.cmd vite build --outDir $stage --emptyOutDir
   ```

3. 在项目目录之外创建部署 JSON，只允许管理员写入，授予服务账号读取权限。以下为虚构域名示例。

   ```json
   {
     "ERP_DEPLOYMENT": "1",
     "PORT": "3001",
     "ERP_PROXY_PORT": "3002",
     "ERP_ALLOWED_HOSTS": "erp.example.invalid",
     "ERP_ALLOWED_ORIGINS": "https://erp.example.invalid"
   }
   ```

   | 配置 | 用途和默认值 |
   |---|---|
   | `ERP_DEPLOYMENT` | `1` 启用部署，省略或 `0` 保持本机模式 |
   | `PORT` | 本机维护端口，默认 `3001` |
   | `ERP_PROXY_PORT` | 同机 HTTPS 代理的后端回环端口，部署时默认 `3002`，须和维护端口不同 |
   | `ERP_ALLOWED_HOSTS` | 部署入口允许的域名，逗号分隔，部署时必填。非标准 HTTPS 端口须同时写在 Host 和 Origin |
   | `ERP_ALLOWED_ORIGINS` | 允许的 HTTPS 写请求来源，逗号分隔，默认由允许域名逐个加上 `https://` |
   | `ERP_BACKUP_COPY_DIR` | 每日完整备份的额外复制目录，默认关闭。使用绝对路径，网络盘使用 UNC 路径 |
   | `ERP_BACKUP_COPY_KEEP` | 目标目录中自动备份的保留份数，默认保留所有，选填正整数 |

   直接运行服务器时可用同名环境变量。计划任务从指定 JSON 加载这些设置，并设置 `NODE_ENV=production`。备份复制使用 ERP 独占目录，位于业务数据和本地备份目录之外，计划任务账号须具有该位置的权限。目标断开时本地备份仍生成，失败显示在今日页，后续定时检查会重试最近一份。

4. 以 Windows 管理员身份打开 PowerShell，先预演。确认路径和名称后，在上线窗口移除 `-WhatIf` 注册任务，按提示输入专用账号凭据。首次启动可在计划任务控制台手动运行。任务开机启动，失败后每隔一分钟重试，最多三次，禁止重叠运行。日志写入指定目录的 `erp.log`，约 10 MiB 轮转，保留七份轮转日志。

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\scripts\install-deployment-task.ps1 `
     -ConfigFile 'C:\ERPConfig\deployment.json' -LogDirectory 'D:\ERPLogs' -WhatIf
   ```

5. 在服务器浏览器打开 `http://127.0.0.1:3001`。空库在此建立首个管理员，随后按职责创建员工账号。恢复的库沿用已有账号。确认计划任务使用正确的 Windows 用户配置目录和 `%LOCALAPPDATA%\ZhixuERP`。DPAPI 将 AI 密钥和机器人 Secret 绑定到原 Windows 账号和机器，换机器或账号时在页面重新输入。启动日志会提示已保存的密钥解密失败。机器人先停用旧电脑的长连接，再启用服务器端；同一机器人只保留一处连接。

### HTTPS 反向代理

代理必须把公网请求送往 `127.0.0.1:3002`，保留原 Host，并用 TCP 对端地址覆盖 `X-ERP-Client-IP`。ERP 用该地址限流，忽略访客提供的 `X-Forwarded-For`。维护端口是本机信任边界，严禁作为任何代理规则的上游。

**Caddy** 使用已配置证书或可从 443 完成验证的证书签发方式。示例从文件读取证书，证书由维护人续期。若只对外开放 443，关闭 Caddy 自动添加的 HTTP 跳转监听。参见 [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。

```caddyfile
{
    auto_https disable_redirects
}
erp.example.invalid {
    tls C:/ERPConfig/erp-fullchain.pem C:/ERPConfig/erp-key.pem
    encode /assets/* gzip
    reverse_proxy 127.0.0.1:3002 {
        header_up X-ERP-Client-IP {remote_host}
    }
}
```

**IIS** 安装 URL Rewrite 和 ARR，在服务器级启用 ARR Proxy，并设置 `system.webServer/proxy` 的 `preserveHostHeader=True`。为专用站点添加仅 443 的 HTTPS 绑定和证书，绑定目标域名。服务器级 URL Rewrite 的允许变量列表添加 `HTTP_X_ERP_CLIENT_IP`。专用站点 `web.config` 的 `system.webServer` 内添加以下规则。参见 [IIS 请求头和服务器变量](https://learn.microsoft.com/en-us/iis/extensions/url-rewrite-module/setting-http-request-headers-and-iis-server-variables)。

```xml
<urlCompression doStaticCompression="false" doDynamicCompression="false" />
<rewrite>
  <rules>
    <rule name="ERP HTTPS to loopback" stopProcessing="true">
      <match url="(.*)" />
      <conditions>
        <add input="{HTTPS}" pattern="^ON$" />
      </conditions>
      <serverVariables>
        <set name="HTTP_X_ERP_CLIENT_IP" value="{REMOTE_ADDR}" replace="true" />
      </serverVariables>
      <action type="Rewrite" url="http://127.0.0.1:3002/{R:1}" appendQueryString="true" />
    </rule>
  </rules>
</rewrite>
```

在 IIS 安装“静态内容压缩”和“动态内容压缩”角色服务。ARR 转发的资源可能按动态内容处理。将以下配置放在站点 `web.config` 的 `configuration` 下，与 `system.webServer` 并列，只为资源路径启用压缩。若站点级配置被锁定，由 IIS 管理员在服务器配置中为该站点和路径设置。参见 [Caddy 响应压缩](https://caddyserver.com/docs/caddyfile/directives/encode) 和 [IIS URL 压缩](https://learn.microsoft.com/en-us/iis/configuration/system.webserver/urlcompression)。

```xml
<location path="assets">
  <system.webServer>
    <urlCompression doStaticCompression="true" doDynamicCompression="true" />
  </system.webServer>
</location>
```

部署后，从首页源码找实际的主 JS 路径，用 GET 请求检查响应头。把示例路径换成该版本的文件名。

```powershell
curl.exe -fsS -D - -o NUL -H "Accept-Encoding: gzip" "https://erp.example.invalid/assets/index-XXXXXXXX.js"
curl.exe -fsS -D - -o NUL "https://erp.example.invalid/"
```

主脚本应有 `Content-Encoding: gzip` 和 `Cache-Control: public, max-age=31536000, immutable`。确认压缩在代理上生效，未声明支持 gzip 的客户端仍能正常访问。首页和前端路由回退的 HTML 应有 `Cache-Control: no-cache`，重载时会重新验证版本。普通静态文件保持默认缓存，API 和财务文件继续使用各自的缓存策略。Windows 部署示例使用 Vite 默认八字符资源哈希。

服务器前还有其他网络代理时，先核对同机代理看到的 TCP 对端地址是否就是预期访客。部署入口设置 Secure Cookie、HSTS，保留现有 CSP、防嵌入和防 MIME 嗅探响应头。远程管理员需重新验证才能进入临时超级管理员模式。部署进程关闭服务器浏览器，员工当前网页的页面控制保留；语音输入在服务器上识别，装了模型就显示。

**只在维护通道（SSH 隧道）可用的功能。** 超级管理员从服务器本机回环地址登录，才算“本机最高管理员”。从公网域名进来，即使进入超级管理员模式也不算。只在维护通道显示的功能主要有：首次建立管理员、数据初始化、永久删除、查看全部已归档记录、直接修改已确认的生产/送货/到货单据、收货更正里的管理员改写，以及 AI 导入免勾选确认。这是有意的设计：这些操作不可逆或绕过业务校验，不对公网开放。

### 防火墙与验收

- Windows 防火墙和云安全组只对员工开放 TCP 443。RDP 仅允许维护者固定来源 IP 或指定管理网。确认管理控制台的备用进入方式。
- 公网访问正确域名并确认 HTTPS、Secure Cookie、HSTS。测试未知 Host、非法 Origin、伪造或缺失访客头，以及普通、只读、财务账号的权限。
- 通过公网管理员检查永久删除、初始化等本机能力受到拦截。远程桌面内用维护地址验证本机管理员功能。
- 在隔离的部署演练实例验证计划任务开机启动、失败重试、轮转、重启会话和证书续期。验证每日备份复制与异机恢复。

### 升级、恢复和回滚

1. 在维护窗口前，用旧版本执行 `npm.cmd run backup`，确认完整备份含校验清单，另存到独立介质。准备新发布目录和构建产物。
2. 维护窗口内先禁用旧计划任务的触发，再在旧发布目录设置维护端口 `PORT`，运行 `npm.cmd run stop` 并确认已退出。把备份恢复到新发布目录，或在停服后迁入数据目录。更新计划任务的工作目录、配置和启动路径。ERP 在启动锁内先保存待升级业务库的快照，之后执行迁移。日志提示快照失败时，排查目录权限和磁盘空间再启动。
3. 检查登录、历史单据、库存、财务和附件。完整恢复需在停服目录运行 `npm.cmd run restore -- "完整备份绝对路径"`。恢复会核验清单并另存原数据。恢复后重新登录，跨机器时重新填写 DPAPI 凭据。
4. 需要回滚时先停新实例，使用旧程序和升级前的完整备份。单独的升级快照只含业务库，适合在隔离目录检查或补救。若新版已经产生业务写入，先备份新版数据并核对差额，再决定如何保留这些写入。数据库只允许一个实例访问。
