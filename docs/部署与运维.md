# 部署与运维

给维护的人看：安装、升级、备份恢复、日常排查、打包。程序内部的机制见[架构说明](架构说明.md)（结构升级和备份见[数据库结构版本](架构/数据库和备份.md)，登录限频见[账号和权限](架构/账号和权限.md)）；还没做的部署工作见[路线图](路线图.md)“服务器上还没做的”。

正式部署只用腾讯云 Ubuntu 24.04 LTS x64 服务器，同机 Caddy 负责 HTTPS；Windows 只作本机使用。两个平台各有安装包，内置 Node.js 24 和原生依赖。

维护命令：Windows 在安装目录双击 `维护命令行.cmd` 后运行 `npm.cmd run …`（源码目录直接用终端）；Linux 用服务账号运行 `scripts/linux/erp.sh`（见“备份和恢复”）。

## 本机（Windows）

- 启动：双击 `启动系统.cmd`，窗口保持打开（源码目录先构建再启动）。停止：双击 `停止系统.cmd`，或原窗口 `Ctrl+C`。
- 地址 `http://127.0.0.1:3001`，端口用 `PORT` 改。要 Node.js 24.15 以上的 24.x。
- 一个数据库只能起一个实例（锁文件 `data/erp.sqlite.running`，异常退出留下的下次自动清理）。
- 数据位置：安装目录的 `data\`（业务库、账号、AI 识别工作区和原件、提示词、日志）、`backups\`；`%LOCALAPPDATA%\ZhixuERP\` 放 DeepSeek 密钥和机器人凭据（`bots\bots.sqlite`），用当前 Windows 账号加密，换电脑或账号要重填。

## Linux 服务器部署

### 安装

全新安装用 `yongle-carton-erp-v<版本>-linux-x64.tar.gz`（现在是 0.9.5），不要复制 Windows 的 `runtime` 或 `node_modules`。先装中文字体（单据排版靠它量字宽，缺了启动会拒绝）：

```sh
sudo apt-get update
sudo apt-get install -y fonts-noto-cjk fontconfig
sudo fc-cache -f
fc-match 'Noto Serif CJK SC'
```

程序解压到 `/opt/yongle-carton-erp`（root 所有，服务账号只读）；数据、备份、凭据在 `/var/lib/yongle-carton-erp/` 下的 `data`、`backups`、`config`。

```sh
sudo sh /opt/yongle-carton-erp/scripts/linux/install-service.sh
sudo editor /etc/yongle-carton-erp/erp.env
sudo systemctl start yongle-carton-erp
sudo journalctl -u yongle-carton-erp -f
```

安装脚本建系统账号 `yongle-erp`，装 systemd 服务并开机自启（崩溃 5 秒后重启，日志进 journald）；不自动首次启动、不覆盖已有配置、不改防火墙。停止、重启用 `systemctl stop|restart yongle-carton-erp`。

### 部署设置

写在 `/etc/yongle-carton-erp/erp.env`（示例 `scripts/linux/erp.env.example`）。**API 密钥和机器人 Secret 不写这里**，在网页设置页填。

| 配置 | 用途和默认值 |
|---|---|
| `ERP_DEPLOYMENT` | `1` 启用部署；省略或 `0` 是本机模式 |
| `PORT` | 本机维护端口，默认 `3001` |
| `ERP_PROXY_PORT` | 给同机 Caddy 的回环端口，部署时默认 `3002`，不能和维护端口相同 |
| `ERP_ALLOWED_HOSTS` | 允许的域名，逗号分隔，部署时必填；非标准 HTTPS 端口要同时写进 Host 和 Origin |
| `ERP_ALLOWED_ORIGINS` | 允许的 HTTPS 写请求来源，默认允许域名逐个加 `https://` |
| `ERP_BACKUP_COPY_DIR` | 每日完整备份另复制到的绝对路径，默认关；要在 systemd 的 `ReadWritePaths` 放行并给服务账号权限 |
| `ERP_BACKUP_COPY_KEEP` | 复制目录里自动备份留几份，默认全留 |
| `ERP_ICP_RECORD` | ICP 备案号原样写（如 `浙ICP备…号`）；从域名打开的网页最底部显示，链到工信部查询。不填不显示 |
| `ERP_POLICE_RECORD` | 公安备案号原样写（如 `浙公网安备 …号`）；同样显示，按号里的数字链到公安查询。不填不显示 |
| `DB_PATH`、`ERP_BACKUP_DIR`、`ERP_CONFIG_DIR` | 业务库、备份根目录、凭据目录。AI 工作区、原件、提示词、日志跟着业务库目录 |

### HTTPS 和维护通道

- 3001（维护）、3002（只给同机 Caddy）都只听本机回环。Caddy 配置照 `scripts/linux/Caddyfile.example`（代理会覆盖 `X-ERP-Client-IP`，不信访客伪造的头），改完先 `caddy validate --config /etc/caddy/Caddyfile` 再重载。示例限了请求体 21MB（程序最大上传 20MB，改上限两处一起改）和读超时（不设写超时，助手要长时间边算边推）。Caddy 前面还有别的代理时，先核对它看到的对端是不是真实访客。
- 防火墙只对员工开 80/443；3001、3002 不开；SSH 22 只放维护者 IP（改规则前确认控制台网页登录能当备用通道）。
- 维护和首次建管理员走 SSH 隧道（隧道不要听 0.0.0.0，维护端口不能当公网代理的上游）：

```sh
ssh -L 13001:127.0.0.1:3001 operator@your-server
```

  然后本机打开 `http://127.0.0.1:13001`；维护电脑同时开着本机 ERP 时改用 `http://localhost:13001`（Cookie 只按主机名区分，否则两边互相顶掉登录）。
- 从域名进来的登录 Cookie 带 `__Host-` 前缀和 Secure（本机和维护通道叫 `erp_session`），部署入口加 HSTS，域名访问的健康检查只回 `ok`；部署时关掉服务器上的浏览器，员工网页里的页面控制照常。

### 从公网和从维护通道能做的事

- **只有维护通道能做**（从服务器本机回环登录的管理员才算“本机管理员”，从域名进来进了超级管理员模式也不算）：首次建管理员、初始化业务数据、数据管理（直接改档案、采购单、库存品、待核对的单据和生产任务；已生效的到货、送货、完工单只能编辑说明或更正，见[单据流转和订单进度](架构/业务主线.md#单据流转和订单进度)）、AI 导入里改已导入的识别结果、复制成新文件和永久删除识别文件、助手的一键清空和数据管理命令。这些不可逆或绕过业务校验，有意不对公网开。
- **从公网也能删：** 没核对的单据有编辑权限就能删；已核对的单据和客户、产品、订单、供应商、采购单、库存品，要超级管理员先进超级管理员模式（账号菜单“系统维护”，输本人密码，15 分钟），确认时再输一次，删前自动快照、写审计。助手删除同样。少了“只能本机删”这道门，账号密码要管好。
- **从公网改共用设置也要先进超级管理员模式：** 管理账号，改 AI 设置（密钥和识别设置）、提示词、机器人凭据、助手工具开关；看、查余额、重新测试不用。
- **登录限频和排队：** 同一账号名从公网 15 分钟输错 20 次就锁（跨地址累计），维护通道照常能登。核对密码同时只算 2 个，排不上回“服务器正忙，请稍后再试。”（页面自动再试一次、不算输错）；维护通道登录和已登录的人验密码排在从域名登录的前面。排队常量（`server/accounts/hash-queue.ts`）按开发机估的，部署后量一次再调。

### 凭据和主密钥

- 凭据目录默认：Windows `%LOCALAPPDATA%\ZhixuERP`；Linux `$XDG_CONFIG_HOME/zhixu-erp`（没设就是 `~/.config/zhixu-erp`），部署时由 `ERP_CONFIG_DIR` 指定。
- Windows 用当前账号的 DPAPI 加密。Linux 用 AES-256-GCM，第一次自动生成 32 字节的 `credentials/master.key`；凭据根目录和密钥目录要属于服务账号、权限 0700，密钥文件 0600、不能是链接，不对就拒绝启动（不退回明文）。不要用 `chmod 777` 解决。
- **主密钥不进任何备份，要单独加密保管。** 备份里的凭据库是密文，丢了主密钥只能到设置页重填。Windows 的凭据不能跨平台解密，迁到 Linux 后要在服务器页面重填 DeepSeek 密钥和机器人 Secret。

## 升级

### 补丁（小版本）

小版本只传变化的程序文件；大版本（如 0.9.0）和依赖有变化时用整包。**服务器上跑的必须是 GitHub 上某个已发布版本**：本机、GitHub、服务器三方除数据、配置、密钥和 `node_modules` 外程序文件逐字节相同。所以先发布（提交、打 `v版本号` 标签、推送、建 GitHub 发布，步骤在 Claude Code 的 `/release` 技能里，发布说明就是 `docs/CHANGELOG.md` 那一节），再在维护电脑的项目目录打补丁（`--host` 是 SSH 配置里的主机名，默认 `yongle-erp`）：

```sh
npm run patch-server -- --dry-run
npm run patch-server
npm run patch-server -- --check
```

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只列差异。正式打之前检查本机没有未提交的改动、当前提交打了 `v版本号` 标签、GitHub 同名标签指向同一提交，不满足就拒绝 |
| `--check` | 列出三方版本和提交、逐个比对文件；一致退出码 0，不一致列原因、退出码 1 |
| `--hotfix "原因"` | 只用于服务器紧急故障：跳过发布检查直接打，服务器记“临时修复，未发布”，事后必须补发正式版 |
| `--base 旧版安装目录 --out 输出目录` | 只生成发布补丁、不上传：输出补丁文件和三个执行脚本 `apply-patch.mjs`、`patch-logic.mjs`、`patch-rollback.mjs`（各带 `.sha256`，清单是 `scripts/patch-server.mjs` 的 `applyScripts`），三个脚本放同一目录运行 |

出问题回滚：检出上一个版本标签再打一次，或用服务器上的回滚副本。

**补丁做了什么：**

- 只取 git 跟踪的程序文件（清单 `scripts/release-files.mjs`，和整包共用）；有没纳入 git 的、被忽略的、符号链接、通不过发布扫描的（数据库、密钥、证书）就拒绝；`package-lock.json` 变了也拒绝（补丁不能重装原生依赖）；`erp.env` 的 `ERP_CONFIG_DIR` 不是绝对路径直接拒绝（程序这时也起不来，先改 `erp.env`）。
- 本机类型检查、把页面构建到临时目录；和服务器逐个比 sha256（Windows 换行转 LF，`.cmd` 保持 CRLF）；上传变化的文件和 `scripts/linux/` 下的三个执行脚本。
- 服务器上先记下补丁开始时间和业务库结构版本、做完整备份、存回滚副本，再停服务、换文件、启动、查健康和版本；读不出版本或备份失败就什么都不改。只改 `/opt/yongle-carton-erp`，不碰配置。
- 同一时间只跑一个（锁 `/run/yongle-carton-erp-patch.lock`）；不怕 SSH 断开，全程记在 `/var/backups/yongle-carton-erp-patches/补丁编号/apply.log`，回滚副本 `rollback.json`（含补丁开始时间）也在那里。每次补丁记在程序目录的 `.release-package`（`commit` 当前提交、`released` 是否正式发布、`patches` 历次补丁）。

断线后查结果：

```sh
ssh yongle-erp sudo tail -n 40 /var/backups/yongle-carton-erp-patches/补丁编号/apply.log
npm run patch-server -- --check
```

日志最后是“补丁已应用”就成了；写着“回滚”或“补丁未应用”就是没打上，照日志处理。

**自动回滚：** 启动失败或 90 秒内健康检查不过，就停服务、换回旧文件，**先换回配置库，再看业务库**。

1. **配置库**（新程序启动时可能已升级了账号、提示词、AI 设置等，见[数据模型](数据模型.md)“其他数据库”，旧程序会因“比程序新”起不来）：
   - 换回来的 `erp.sh` 有 `revert-config-upgrades` 动作：以服务账号运行它，把补丁开始以后升级过的配置库换回升级前备份；它报失败（见“备份和恢复”的“换回配置库”）就转人工。
   - 没有这个动作（0.9.0 的程序）：在数据目录、配置目录各自的 `snapshots/` 里找补丁开始以后的配置库升级前备份（每个库最新一份），只读看库现在的版本，等于备份写的“到第几版”才算升级过。一个都没有就往下走；有、或读不出某个库的版本，转人工（提示列出是哪几个库和备份）。
   - **转人工：** 服务保持停止，照打印的步骤逐个换：把现在的库连同 `-wal`、`-shm`、`-journal` 改名留在 `snapshots/` 下（`<库文件名>-before-revert-manual-时间`，不要删），再把升级前备份复制回去。命令跑过但失败的，步骤只列还没换回的；之后又读不出版本时，列出补丁开始以后全部的配置库升级前备份，逐个确认库的版本等于备份写的“到第几版”才换。步骤里写明业务库变没变：没变换完直接启动，变了或判断不了接着用补丁前备份恢复。
   - 换回后，新程序运行期间改的配置（新账号、长期记忆、提示词、AI 设置、机器人设置）在换下来的 `-before-revert-` 文件里，要时人工补录；账号库换回后没有会话，**所有人要重新登录**。
2. **业务库：** 结构版本没变 → 直接启动旧程序；新版本升级过 → 用补丁前的完整备份恢复再启动（之后的写入不在库里，原数据目录另存为 `data.before-restore-时间`，要时人工补录，所有人重新登录）；判断不了（读不出版本、找不到备份、停服务失败）→ 服务保持停止，照打印的步骤手动恢复，不要直接启动旧程序。

### 整包

1. 备份（`npm.cmd run backup` 或 `erp.sh backup`），停止服务。
2. 新版本解压到新目录（Windows 把旧目录的 `data\`、`backups\` 复制过去；Linux 替换 `/opt/yongle-carton-erp`，数据目录不动）。
3. 启动。结构有变时启动先拍升级前快照，再在一个事务里按编号逐步升级，失败整体退回、数据不动，启动窗口写明原因；配置库同样，升级前备份在各库旁边的 `snapshots/`。
4. 退回旧版本：停服务、换回旧程序，先换回配置库（Linux `erp.sh revert-config-upgrades`；Windows 在旧目录的维护命令行手动运行 `npm.cmd run revert-config-upgrades`——旧目录的 `data\` 没动过，但 AI 设置、机器人设置在新旧共用的 `%LOCALAPPDATA%\ZhixuERP\`，不换回旧程序打不开），再看业务库：结构版本变了就用第 1 步的备份恢复。旧程序没有这条命令时照上面“转人工”做。影响同补丁回滚。

### 0.9.0 以前的旧数据

0.9.0 起业务库从空库开始（建表定为第 20 版）：**0.9.0 以前的业务库和备份不能升级或恢复；从 0.8.x 升只能整包，不能打补丁**（打了会因旧库启动失败、自动换回旧文件）。

- **碰到旧业务库：** 拒绝启动（“这是 0.9.0 以前的旧业务数据库”），旧库不动，提示写明移走哪几样。先用 0.8.4 做一次完整备份另存别的磁盘（以后只有 0.8.4 能恢复），再在业务库目录（本机安装目录的 `data/`，服务器 `/var/lib/yongle-carton-erp/data/`）把这三样**移走保存、不要删**：`erp.sqlite`（连同 `-wal`、`-shm`）、`import-archive/`、`ai-imports/`（识别工作区按编号引用客户产品，接不上新库）。再启动建空库，然后建管理员和各账号，在“设置 → API 配置”重填 DeepSeek 密钥、“设置 → 消息接入”重填机器人的应用编号和 Secret。
- **旧配置库：** 账号、AI 设置、提示词、助手工具设置认出是 0.8.4 的就整个删掉重建（`server/core/backup/versioned-sqlite.ts`）；机器人设置在配置目录 `bots/bots.sqlite`，旧位置不再读。提示词、助手工具开关、单据模板、财务科目和凭证模板都回到默认。
- **可删的旧文件：** 配置目录的 `wecom/`；数据目录 `ai-prompts/` 里的 `shipping-marks.sqlite`、`purchase-orders.sqlite`、`customer-deliveries.sqlite`。
- **退回 0.8.4：** 停掉新程序、换回 0.8.4，用 0.8.4 做的完整备份恢复（配置库已重建，只放回移走的三样不够）。0.9.0 以后录的数据带不回去。

## 客户端更新包

安卓 App 和 Windows 客户端（`apps/`）的“检查更新”先读服务器上的版本清单，再下载安装包。两者放在同一域名下的固定目录，由 Caddy 直接当静态文件发，不经 ERP、不用登录：

| 地址 | 是什么 |
|---|---|
| `https://erp.nbyongle.cn/app-update/android/manifest.json` | 安卓版本清单（格式见 `apps/android/docs/构建与测试.md`“应用内更新”） |
| `https://erp.nbyongle.cn/app-update/android/<安装包>.apk` | 安卓安装包 |
| `https://erp.nbyongle.cn/app-update/windows/latest.json` | Windows 版本清单（Tauri 格式，见 `apps/desktop/docs/构建与测试.md`“应用内更新”） |
| `https://erp.nbyongle.cn/app-update/windows/<安装包>.exe` | Windows 安装包 |

- **服务器目录：** `/srv/yongle-erp-app-update/android/`、`/srv/yongle-erp-app-update/windows/`，属于维护账号、Caddy 能读（目录 0755、文件 0644）；不在 ERP 的安装和数据目录里，升级、备份恢复都不碰。文件名只用字母、数字、`.`、`-`、`_`（Windows 打包出的中文名上传时改掉，清单写改后的名字）。没有文件时 `/app-update/` 回 404，不交给 ERP。
- **Caddy：** 写法只在 `scripts/linux/Caddyfile.example` 的 `/app-update/` 一段（清单不让缓存），服务器上已照它配好；以后改完先 `caddy validate` 再重载。
- **发新版的顺序：** **先**传安装包、确认能从域名下载且 sha256 一致，**再**传清单（反了客户端会看到新版却下不到）。打包、签名、清单写法见两个外壳各自 `构建与测试.md`“正式发布的顺序”。
- **客户端里的地址：** 打包时写进安装包，都已填好：更新清单地址（安卓 `releaseUpdateUrl`，Windows `config/app.json` 的 `updateUrl`、`updatePubkey`；没填就发出去的客户端永远不会自己更新），正式版打开的 ERP 地址（安卓 `apps/android/app/build.gradle.kts` 的 `releaseUrl`、Windows 的 `erpUrl`）。第一个正式版 0.1.0 已于 2026-11-21 放进更新目录：安卓 `https://erp.nbyongle.cn/app-update/android/yongle-erp-0.1.0.apk`，Windows `https://erp.nbyongle.cn/app-update/windows/yongle-erp-0.1.0-x64-setup.exe`；第一次手动下载安装，之后客户端自己提示更新。

## 备份和恢复

| 类型 | 说明 |
|---|---|
| 手动完整备份 | `npm.cmd run backup`，生成 `backups/full-时间/`，运行中可以做；唯一的手动备份命令 |
| 自动备份 | 服务运行时每天一次，`backups/auto-时间/`，留最近 14 份；失败时今日页提示 |
| 删除前快照 | 删除、初始化、本机管理员直接改订单前自动拍，`data/snapshots/`，拍不成就停止操作。24 小时内全留，更早留 20 份。只含业务库，不含原件 |
| 升级前快照 | 业务库要升级时拍，`data/snapshots/upgrade-v旧版-to-v新版-时间.sqlite`，留最近 3 份 |
| 配置库升级前备份 | 配置库要升级时做，在库旁边的 `snapshots/`（如 `data/security/snapshots/`、配置目录的 `ai/snapshots/`），叫 `<库文件名>-upgrade-v旧版-to-v新版-时间.sqlite`。同一个版本对只留最新一份，最多留 3 个版本对；账号库的不带会话。补丁回滚换回配置库时用；确认不再退回旧程序后可手动删 |
| 换下来的配置库 | 换回配置库时换下来的那份，同一个 `snapshots/` 下的 `<库文件名>-before-revert-时间.sqlite`（手动换回的叫 `-before-revert-manual-时间`，可能带 `-wal` 等）。里面是新程序运行期间的配置，账号库已去掉会话。不自动清理，补录完可删 |
| 升级没做完留下的备份 | 某一步升级自己结束了事务（程序问题）、库成半截时，这次的升级前备份改名为 `snapshots/` 下的 `<库文件名>-before-unfinished-v旧版-to-v新版-时间.sqlite`。不自动清理；**有它这个库以后都打不开**。处理：停程序，把它移到库文件的位置覆盖半截的库（附属的 `-journal` 等一起删），换上修好的或旧版程序启动 |

Linux：

```sh
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh backup
sudo systemctl stop yongle-carton-erp
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh restore /absolute/backup-directory
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh reset-password 用户名
sudo -u yongle-erp /opt/yongle-carton-erp/scripts/linux/erp.sh revert-config-upgrades [补丁开始时间]
```

- **换回配置库：** `revert-config-upgrades`（Windows `npm.cmd run revert-config-upgrades -- [时间]`），先停服务；补丁回滚和整包退回时用（见“升级”）。把比当前程序新的配置库换回从当前版本升上去时的升级前备份；给了时间（如 `2026-11-21T10:00:00.000Z`）只用这之后做的。逐个打印换回了哪个库、用的哪份备份、换下来的文件在哪，换回账号库会提示所有人重新登录；没有要换的打印“没有比当前程序新的配置库，不用换回。”。换不回的逐个打印原因、那个库不动、退出码 1（补丁回滚时就转人工）。换不回的三种情况：
  - 找不到从当前版本升上去的升级前备份：确认程序版本对不对，或到 `snapshots/` 找合适的备份手动换。
  - 库旁边还有 `-wal`、`-shm`、`-journal`（上次没正常关，可能有没写完的改动）：确认服务已停，照“升级”里转人工的做法换；拿不准交给维护人员。
  - 默认位置算不出来（多半是 `ERP_CONFIG_DIR` 不是绝对路径）：改成和服务同一个绝对路径，用和服务同一套设置再运行。
- **备份里有：** 业务库、账号、AI 工作区和原件、归档、提示词、助手工具设置、出错记录，以及加密的 AI 配置和机器人配置（在 `_extra/`，机器人的叫 `bots.sqlite`）。清单 `manifest.json` 记程序版本、业务库结构版本和各配置库版本。
- **不要直接复制 `erp.sqlite` 当备份：** 运行中是 WAL 模式，复制出来可能缺最近的写入，恢复时会被拒。
- **恢复：** 先停服务，再 `npm.cmd run restore -- "备份目录绝对路径"`，用和服务同一套 `DB_PATH`、`ERP_CONFIG_DIR`。恢复前的 `data/` 另存为 `data.before-restore-时间`，中途失败自动退回。也收单个业务库文件（备份里的 `erp.sqlite` 或 `data/snapshots/` 下的快照），只恢复业务库。
- **恢复前全部校验：** 清单、sha256、每个库都过了才动数据，一个不过整份拒绝。拒绝：WAL 模式的副本（旧格式备份、直接复制的库）、0.9.0 以前的业务库和配置库、比程序新的、版本记录不完整的、不是本系统的、结构被改过的。配置库比程序旧但在 0.9.0 以后的照常恢复，启动时升级。`_extra/` 里的 AI 和机器人配置不覆盖本机、不论版本只查完整性；认不出是哪个配置库的文件也只查完整性，恢复完列出这些“只查了完整性的文件”。
- 业务库比程序新（如补丁回滚后）也能备份，清单标 `newerSchema`，只能用支持该版本的程序恢复。
- **离机保存：** 定期把备份复制到别的磁盘（服务器上另一个目录不算，要挂载或传出去），定期做一次隔离的恢复演练。

## 日常维护和排查

### 每日清理

服务启动 5 分钟后第一次跑，之后每小时看一次、满 24 小时才再清，库正忙就等下个小时；清了东西日志写一行“每日清理：……”。

- 防重复提交记录留 90 天。
- 订货单、送货单导出的文件内容留 180 天，之后只删文件，记录、单号、交付状态留着。
- 收件箱待处理、已忽略的消息 180 天后连附件删，已处理的（含转成单据的）留着。
- 删数据空出的空间还给磁盘（库大时稍慢）。
- 连续运行满 24 小时和关闭时更新一次查询统计。

### 排查问题

- **问助手：** 员工说点了没反应、保存不了，可以让助手查最近出错和被拒的请求（服务端和页面上报的，留 30 天；普通账号只看自己的，超级管理员看全部）、按人按时间的修改记录、后台任务；超级管理员还能看运行日志、登录记录和程序代码（只读）。
- **日志在哪：** 业务库目录下的 `logs/`：`run.log` 运行日志（满 2MB 轮换成 `run.log.1`），`problems.sqlite` 出错记录。Linux 还可以 `journalctl -u yongle-carton-erp`。
- **“数据没有保存：有内容不符合数据规则，请联系维护人员。”**：数据库规则（状态取值、真实日期、单位只收“只”“张”、金额不为负等）挡住了写入，什么都没存——程序本该先拦，是程序问题。日志里以 `[数据规则]` 开头的一行写明入口和哪条规则（不带写入的值），交给开发。
- **启动被拒绝（数据都不动）：**

| 启动窗口的提示 | 原因和做法 |
|---|---|
| 这是 0.9.0 以前的旧业务数据库 | 按“0.9.0 以前的旧数据”移走旧库 |
| 数据库比当前程序新 | 多半是回滚只换回了程序。换回新程序，或用补丁前的完整备份恢复 |
| 这个文件不是本系统的业务数据库 | `DB_PATH` 指错了 |
| 业务数据库的版本记录不完整 | 库被改坏了，用最近的完整备份恢复 |
| 业务数据库的表结构和当前程序对不上 | 版本是当前版、表结构却不一样（直接改了建表或被数据库工具改过），提示列出差在哪几张表。正式数据用最近的完整备份恢复；开发库移走再启动建新库。升级走完后对不上也一样，整次升级退回 |
| 某个配置库比当前程序新 | 多半是回滚只换回了程序。停服务后运行 `revert-config-upgrades`，或换回新程序 |
| 某个配置库从第 a 版升级到第 b 版失败，已整体退回 | 文件没动。换回旧版程序继续用，提示交给维护人员 |
| 某个配置库升级停在某一步：这一步自己结束了事务，升级没有做完 | 程序问题，唯一文件可能已改动的情况：库是半截的，升级前备份已改名成 `-before-unfinished-`，以后打开都拒绝。照提示的“处理办法”和“备份和恢复”里“升级没做完留下的备份”做，提示交给维护人员 |
| 某个配置库要从第 a 版升级到第 b 版，升级前备份没有做成 | 没开始升级、文件没动。查那个目录的磁盘空间和读写权限后再启动 |
| 某个配置库比基线（第 N 版）旧，要删掉重建，但文件删不掉 | 关掉占用它的程序再启动 |

### 账号

- 第一次使用在登录页建管理员（服务器上走维护通道）。
- 员工忘记密码在登录页提交，管理员在“账号管理”确认后发临时密码。

### 消息机器人

企业微信、飞书、钉钉都用长连接，不用公网地址，服务器能出站访问就行：`openws.work.weixin.qq.com`、`open.feishu.cn`（和它给的长连接地址）、`api.dingtalk.com`（和它给的 Stream 地址，回复发到 `*.dingtalk.com`）。三家可同时开，在“设置 → 消息接入”各一张卡片，填好点“保存并连接”，显示“已连接”才收得到。

- **企业微信：** ① 管理后台建智能机器人，API 模式选“使用长连接”；② 复制 Bot ID、获取 Secret；③ 设好哪些人能用；④ ERP 卡片填好、点“保存并连接”；⑤ 单聊发文字、图片、文件试一下。
- **飞书：** ① 开发者后台建“企业自建应用”；② 加应用能力“机器人”；③ 开通权限“读取用户发给机器人的单聊消息”（`im:message.p2p_msg:readonly`）、“接收群聊中 @ 机器人消息事件”（`im:message.group_at_msg:readonly`）、“获取与发送单聊、群组消息”（`im:message`，下载文件和回复要它）；④ “凭证与基础信息”复制 App ID、App Secret；⑤ 先在 ERP 卡片填好、点“保存并连接”（飞书要求长连接在线才能保存下一步）；⑥ “事件与回调”订阅方式选“使用长连接接收事件”；⑦ 添加事件“接收消息”（`im.message.receive_v1`）；⑧ 建版本、设可用范围、发布；⑨ 单聊发文件试一下。
- **钉钉：** ① 开发者后台建“企业内部应用”；② “凭证与基础信息”复制 Client ID、Client Secret；③ 加应用能力“机器人”，接收模式选“Stream 模式”，发布机器人；④ 开通“企业内机器人发送消息权限”（`qyapi_robot_sendmsg`，下载文件要它）；⑤ 设可见范围并发布；⑥ ERP 卡片填好、点“保存并连接”；⑦ 单聊发文件试一下。
- **同一个应用只连一处：** 企业微信后连的顶掉先连的、不会抢回；飞书、钉钉把消息随机发给其中一处，更难发现。测试实例别和正式实例连同一个应用，切换时先断旧的再连新的。
- **卡片上的状态：**

| 状态 | 意思和做法 |
|---|---|
| 已连接 | 收得到 |
| 连接中、连接断开，正在重试 | 网络断了、对方限流或临时出错，程序按退避自己重试（红字“××暂时连不上（错误码 N），正在重试”）；一直不好再查服务器出站网络 |
| 连接被拒绝 | 凭据或后台配置不对，不再重试，红字写原因（如“钉钉拒绝连接（错误码 401）：请检查 Client ID 和 Client Secret。”），改对后点“保存并重新连接” |
| 红字“已保存的 Secret 在这台机器上解不开……请重新填写 Secret。” | 换了服务器、平台或服务账号，重填一次 |
| 已被其他连接顶替 | 只有企业微信有：同一个机器人在别处连上了 |

- 系统关着时收不到消息，官方没说之后会不会补发。

## 打包和 Linux 验证

两个包用同一个脚本，必须在各自平台的 Node 24 x64 上打（`--target win-x64` 或 `linux-x64`），不能复制别的平台的原生依赖；主密钥不进安装包。程序文件清单在 `scripts/release-files.mjs`（运行时要用的新脚本或目录要加进去），发布扫描规则在 `scripts/release-scan.mjs`，整包和补丁共用。

- **Windows 包：** 开发机上 `npm run package -- --out <项目外的目录>`；检查也在开发机上跑（`npm run check`）。
- **Linux 包和 Linux 上的测试：** 在服务器的打包目录 `/home/ubuntu/build/` 里做，和 `/opt` 里正在运行的程序、`/var/lib` 下的数据分开，用程序自带的 Node，全部是临时目录里的虚构数据。自己的检查不放在 GitHub 上跑（那边的机器慢，靠时间的测试会误报）。服务器比开发机慢，设 `CI=1` 让慢测试只报不拦；代码检查、类型这些和平台无关的只在开发机上跑（服务器内存小，不在上面跑）：

  源码从开发机送过去（服务器在国内，连 GitHub 时通时断）：开发机上 `git bundle create v<版本>.bundle v<版本>`，`scp` 到服务器的 `/home/ubuntu/build/`；提交号和 GitHub 上的标签是同一个。

```sh
export PATH=/opt/yongle-carton-erp/runtime/node/bin:$PATH
cd /home/ubuntu/build
git clone --branch v<版本> v<版本>.bundle src-v<版本>
cd src-v<版本>
export LOCALAPPDATA="$(mktemp -d)" CI=1
export ERP_CONFIG_DIR="$LOCALAPPDATA/config" DB_PATH="$LOCALAPPDATA/unused.sqlite" ERP_BACKUP_DIR="$LOCALAPPDATA/backups"
npm ci
npm test
npm run test:release
npm run package -- --target linux-x64 --out /home/ubuntu/build/out
```

- **装之前验包：** 核对 sha256，解压到单独的目录，在里面用包里的 Node 跑 `runtime/node/bin/node --import tsx scripts/linux/verify-runtime.mjs`（运行环境、原生依赖、字体、单据排版）。`scripts/linux/verify-package.mjs`（干净目录启动、建管理员、登录、导出、备份恢复）有两处跟不上程序了，修好之前只能看到“启动、建管理员、登录”这一段，见[路线图](路线图.md)“已知问题”。

## 项目里不能随手删的

- 数据目录、备份目录、用户配置目录受保护：整理项目时不清库、不初始化、不删原件、归档、审计和凭据。
- `node_modules`、`dist`、`.build-tmp-*`、`.playwright-cli` 和测试日志能由安装、构建、测试重新生成。
- 本机的 `work/`、`output/`、`outputs/` 混有验收样张、截图、旧克隆和安装包，不能只凭目录名删，先查 Git 状态、引用和来源。
